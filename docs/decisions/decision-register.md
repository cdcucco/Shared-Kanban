# SharedKanban decision register

This register is the canonical set of Phase 0 decisions for SharedKanban. It was synthesized from three independent architecture proposals and three independent judgments of those proposals: for each topic the majority-preferred proposal is the base, the elements the judges recommended grafting are folded in, and every flaw and cross-topic inconsistency the judges found has been resolved so that concurrency, offline replay, idempotency, ranking, and the activity log describe one model. The brief's hard constraints are unchanged: native SwiftUI; Swift/Vapor + Fluent + PostgreSQL; Mac mini hosting with Docker Compose and a launchd escape hatch; exactly 3 or 4 active columns per project in release 1; the required templates Home Projects (Backlog, To Do, In Progress, Complete) and Restaurants to Try (Backlog, Scheduled, Complete); every drag has a non-drag alternative; the server is authoritative with cached reads and queued offline mutations; no AI component gets raw database or filesystem access; destructive and membership-changing MCP actions require explicit confirmation; no secrets in the repository. Five decisions are expanded by architecture decision records that live beside this file: ADR-0001 (`0001-vapor-fluent-postgresql.md`) expands D11, ADR-0002 (`0002-swiftdata-as-cache.md`) expands D12, ADR-0003 (`0003-websockets-realtime.md`) expands D13, ADR-0004 (`0004-local-attachment-storage.md`) expands D14, and ADR-0005 (`0005-mcp-proposal-confirmation.md`) expands D15. Written on 2026-10-01; exact platform and library versions are deliberately not asserted here and are listed under "Assumptions to verify at Phase 1". Error codes throughout are the snake_case codes defined in D22.

## D01 — iPhone board navigation and cross-column dragging

### Decision

Structure. The navigation bar shows the project title. Directly below it a column switcher bar shows one pill per active column: title, active-task count, and `count/limit` when a WIP limit is set; the selected pill is accent-tinted and underlined; every pill is at least 44pt tall; the bar has the adjustable accessibility trait and exposes the selected state. The board is a `ScrollView(.horizontal)` containing a `LazyHStack` with `.scrollTargetLayout()`, `.scrollTargetBehavior(.viewAligned)` and `.scrollPosition(id:)` bound to `BoardSelection.columnId` (D02). Each column page is the container width minus 24pt so the neighbor column peeks and signals horizontal movement. Cards inside a page live in a `ScrollView` plus `LazyVStack`, never in `List`: `List.onMove` cannot cross lists, row swipe gestures fight the paging gesture, and drop insertion inside `List` is unreliable. There are therefore no swipe actions; every card carries a 44pt ellipsis button and a `.contextMenu`.

Drag. Cards adopt `.draggable(TaskDragItem)` where `TaskDragItem: Transferable, Codable` carries only `{projectId, taskId}` under the custom UTType `com.sharedkanban.task`, declared in Info.plist under `UTExportedTypeDeclarations`. There is no `.text` representation (task titles must not leak into other apps during an iPad drag); a "Copy title" menu item exists instead. Drop targets, in build order: (1) each switcher pill is a `.dropDestination(for: TaskDragItem.self)` that appends the card to the end of that column (`afterTaskId` = last active task, `beforeTaskId` = nil); (2) the column body appends to the end; (3) each card row is a drop destination that decides before/after from the pointer's y position relative to the row midpoint and shows a 2pt rounded accent insertion bar; (4) 44pt top and bottom zones inside each column nudge the vertical `scrollPosition` while targeted, because SwiftUI drag has no vertical auto-scroll; (5) 44pt leading and trailing edge zones page to the adjacent column when `isTargeted` has stayed true for 400 ms, and the drag continues so the user drops at an exact position. Items 1 to 4 are the Phase 6 exit gate; item 5 is built last and removed if programmatic paging cancels the drag session on a real device, in which case the pills remain the cross-column path. A drop whose payload `projectId` differs from the board's project is refused. If a realtime event archives the dragged task or archives the destination column while the drag is in flight, the drop is refused and the rejection banner is shown.

Feedback. The targeted column tints its background with `Color.accentColor.opacity(0.08)`; `.sensoryFeedback(.selection, trigger:)` fires on target change and `.success` on commit. With Reduce Motion the insertion bar crossfades instead of sliding and no spring animation is used. When a drop would exceed a WIP limit the pill and the insertion bar show `count/limit` in the warning color with the `exclamationmark.triangle` symbol and a VoiceOver suffix "over the limit of N"; the drop is never blocked.

Commit and rejection. Every drop and every menu move computes `(destinationColumnId, afterTaskId, beforeTaskId)` from the cached column order and calls the single `MoveCoordinator.move(...)`, which applies the move optimistically and submits the D06 contract with a fresh operationId. On rejection the card animates back to the server position (spring, or crossfade under Reduce Motion) and a bottom `safeAreaInset` banner shows the plain-language reason for 4 s ("Moved by Sam a moment ago. Your move was not applied."), also posted as `AccessibilityNotification.Announcement`.

Non-drag alternatives, available on every card through the ellipsis button, the context menu, `accessibilityAction`s and the task detail toolbar: Move to Column… (a sheet listing the active columns with the current one checked, and a Top / Bottom placement choice), Move to Top, Move Up, Move Down, Move to Bottom, Assign, Due Date, Archive, Copy title. Long-press without movement opens the context menu; long-press followed by movement starts the drag. The VoiceOver label is "<title>, in <column>, assigned to <name>, due <relative>, overdue" as applicable, with the value "waiting to sync" while a pending operation exists (D08).

Adding tasks. An "Add task" button sits at the bottom of every column page and a toolbar "+" creates in the visible column; new tasks append to the bottom of the column. Empty columns show a one-line instruction.

System chrome. Toolbars, sheets and the switcher bar use the current SDK's system materials and defaults; the design-system doc does not opt out of the SDK's design language (verify the SDK's chrome behavior for the pinned header at Phase 4).

### Rationale

One column per page is the only layout that keeps titles readable at Dynamic Type sizes on a 375pt screen. Pills as drop targets plus edge-dwell paging are the two cross-column mechanisms that native `Transferable`/`draggable`/`dropDestination` supports without custom gesture recognizers, and together they cover "throw it to Complete" and "place it exactly". The menu alternatives guarantee VoiceOver, Switch Control and keyboard users never need the drag gesture, give UI tests a deterministic path, and are mandatory under the brief.

### Rejected alternatives

Two half-width columns on iPhone (titles clip at large Dynamic Type); `List` with `onMove` (single list only, no cross-column drops); a custom UIKit drag with a floating card overlay (fights the system preview and breaks VoiceOver); full-screen paging without a peek (users do not discover horizontal movement); a two-step "drag then pick column" modal as the only path (slow for the common case); a `.text` drag representation (leaks titles to other apps).

### Consequences

The column switcher is a custom control that needs its own accessibility and keyboard focus handling. Cards are rendered in a LazyVStack, so the ellipsis button is the discoverable alternative to swipe actions. The client must keep a per-column ordered array in memory to compute neighbors for both drag and menu moves. The UTType declaration and the drag payload shape are part of the Phase 4 prototype so Phase 6 only wires the move contract.

### Open risks

The interaction between `.contextMenu` and `.draggable` long-press timing, drop targets inside a horizontally paging ScrollView, and programmatic paging during a live drag session are unverified until Phase 6 on a real device; the pills and the menu are the guaranteed fallback. The pinned switcher bar may need adjustment to the current SDK's system chrome; verify at Phase 4.

## D02 — iPad NavigationSplitView structure and compact-window behavior

### Decision

Split view. `NavigationSplitView(columnVisibility: $visibility, preferredCompactColumn: $compactColumn)` with `.navigationSplitViewStyle(.balanced)`. The sidebar lists projects in Active and Archived sections with an Account row at the bottom; the detail column is `BoardView`. Sidebar visibility stays `.automatic`; the system collapse button is kept.

One board, two layout modes. `BoardView` is the same view on iPhone and iPad and takes `layoutMode ∈ {.multiColumn, .paged}`. The board pane's own width is observed with `.onGeometryChange`; `UIScreen` and device idiom are never consulted. With `n` active columns, `fitsAll(w) = w >= n * 240 + 16 * (n + 1)` (784pt for 3 columns, 1040pt for 4). The mode is `.multiColumn` when `horizontalSizeClass == .regular` and `fitsAll(boardWidth)`; the column width is then `clamp((w - 16 * (n + 1)) / n, 240, 380)` and the row is centered. In every other case (compact size class, Slide Over, one-third Split View, narrow Stage Manager windows, any width that does not fit) the mode is `.paged`, which is exactly the D01 iPhone board rendered inside the detail column with the sidebar collapsed into stack navigation. There is no intermediate two-column mode. Mode changes animate only when Reduce Motion is off.

Task detail. Task detail is a trailing `.inspector(isPresented:)` with `.inspectorColumnWidth(min: 320, ideal: 360, max: 420)` when the size class is regular and either `fitsAll(boardWidth - 360)` holds or the board is already `.paged`; otherwise it is presented with `.sheet` using the large detent. Opening the detail therefore never flips the board between modes. In the compact size class the system presents the inspector as a sheet anyway; both presentations share one `TaskDetailView`.

Selection. A single `@Observable BoardSelection { projectId, columnId, taskId, isDetailPresented }` holds the current place so width transitions never lose it; `projectId` and `taskId` are persisted with `@SceneStorage`. Release 1 enables a single scene (`UIApplicationSupportsMultipleScenes = NO`).

Pointer and keyboard. Cards use `.hoverEffect(.lift)`; drop zones highlight on hover; a direct pointer or trackpad drag starts immediately. Cards are `.focusable()` with a `@FocusState<UUID?>` focus model that VoiceOver and Full Keyboard Access share. Shortcuts: Cmd-N new task in the selected column; Cmd-1 to Cmd-4 select column; arrow keys move card focus; Cmd-Option-Up/Down reorder; Cmd-Option-Left/Right move to the adjacent column; Return opens detail; Cmd-Delete archives with confirmation; Escape closes the inspector or sheet. While a text field in the detail has focus, shortcuts that edit the board are disabled.

Tests. Snapshot or UI tests run at widths 320, 375, 507, 744, 834, 1024, 1194 and 1366pt, and in Slide Over, one-third and one-half Split View, full screen and a narrow Stage Manager window, with Dynamic Type at the accessibility XL size to confirm the 240pt column minimum still holds two or three lines of title.

### Rationale

Apple's HIG prescribes split views for hierarchy on iPad and requires layouts to adapt to window width; sizing from the pane rather than the device is the only rule that survives Stage Manager, Split View and Slide Over uniformly. The formula derives the threshold from column count and a tested minimum column width instead of a magic number. Deciding inspector-versus-sheet from the post-inspector width removes the layout thrash that otherwise happens the moment a card is tapped. One board view with two modes is less code and fewer tests than three layouts.

### Rejected alternatives

Three-column `NavigationSplitView` with task detail as the third column (fights the board for width and collapses unpredictably); a custom side panel for task detail (does not adapt to compact width); fixed device-based breakpoints (break under Stage Manager); an intermediate two-columns-side-by-side mode (a narrow, rarely reachable band for extra tests); multiple scenes in release 1 (scene state sync for no household payoff).

### Consequences

Views are written against pane width, never `UIScreen`. The board view must not assume iPhone chrome. The design-system doc states the 240/380pt column bounds, the 16pt gutter and the inspector widths. The keyboard focus model is built in Phase 4 so Phase 6 drag work does not retrofit it.

### Open risks

`.inspector` presentation inside a `NavigationSplitView` detail column in Stage Manager and Slide Over, and `onGeometryChange` behavior during live resizing, are verified at Phase 4 on the minimum OS; if the inspector proves unreliable in compact windows, task detail falls back to `navigationDestination` in compact width and the inspector is used only in regular width.

## D03 — Roles and permission matrix

### Decision

Roles are `owner`, `admin`, `editor`, `viewer`, stored in `project_members.role`. Every check goes through one function, `ProjectAuthorizer.require(_ capability: Capability, project:, user:)`, where `Capability` is a Swift enum; REST and MCP call the same function and the UI never relies on its own hiding.

Matrix (Owner / Admin / Editor / Viewer):

- read project, columns, tasks, comments, activity, members, and download attachments: Y / Y / Y / Y
- list pending invitations: Y / Y / N / N
- create, edit, move, archive and restore tasks; add comments; add attachments; archive completed tasks (bulk): Y / Y / Y / N
- edit or delete own comment; delete own attachment: Y / Y / Y / N
- delete another member's comment or attachment: Y / Y / N / N
- permanently delete an archived task: Y / Y / N / N
- create, rename, recolor, reorder, set WIP limit, set done column, archive and restore columns: Y / Y / N / N
- rename project; archive and unarchive project: Y / Y / N / N
- create invitations for editor or viewer; revoke any invitation: Y / Y / N / N
- create an invitation for admin: Y / N / N / N
- change a member between editor and viewer; remove an editor or viewer: Y / Y / N / N
- promote to admin, demote an admin, remove an admin: Y / N / N / N (an admin may demote themselves to editor)
- transfer ownership; permanently delete the project; restore a deleted project: Y / N / N / N
- leave project: N / Y / Y / Y
- manage own notification settings; be an assignee: Y / Y / Y / Y (viewers can be assigned and receive the assignment notification and due reminders; they cannot edit the card)

Invariants. Exactly one owner per project: `projects.owner_id` plus a partial unique index on `project_members (project_id) WHERE role = 'owner'`, plus a deferrable constraint trigger that asserts at commit that the owner member row's `user_id` equals `projects.owner_id`. Nobody may change the owner's role or remove the owner. A user with `users.deleted_at` set is a non-member everywhere (their membership rows are deleted in D09 anyway).

Ownership transfer. `POST /v1/projects/{id}/transfer-ownership {operationId, newOwnerUserId, expectedVersion}`; the target must be an existing member; in one transaction the target becomes owner, the previous owner becomes admin, `project.version` increments, and `project.ownership_transferred` is recorded. The UI requires a confirmation alert naming the new owner. No MCP tool exists for it. Account deletion (D09) uses this same code path before removing the previous owner's membership.

Owner leaving. `DELETE /v1/projects/{id}/members/{selfId}` by the owner returns 409 `owner_must_transfer` when other members exist; the UI replaces Leave with "Transfer ownership" and "Delete project". When the owner is the project's only member, Leave is presented as Delete project and behaves as project deletion.

Role changes. `PATCH /v1/projects/{id}/members/{userId} {operationId, role, expectedVersion}` where `expectedVersion` is the member row's version, so two admins changing the same member concurrently get a 409 `version_conflict`. The affected user receives `member.role_changed` in realtime and the client drops edit affordances immediately.

Removal effects. The membership row is deleted (events remain). The removed user's `assigneeId` on that project's active tasks is cleared, one `task.updated` event per task with `changes.assigneeId` and `via = system`. Their comments, attachments and activity remain attributed. Sessions are not revoked; from the next request every REST call for that project returns 404 `not_found`, the realtime hub drops their subscriptions (D13), and any queued offline operation for that project fails with `not_found` (D08).

Archived project. Reversible, owner/admin. While archived every mutation returns 409 `project_archived` except unarchive, leave, member removal and notification settings; queued offline operations for an archived project fail with `project_archived`.

Project deletion. Owner only. `DELETE /v1/projects/{id}` sets `deleted_at`, hides the project immediately for everyone, auto-revokes pending invitations, and drops realtime subscriptions. The owner can restore it from Settings → Deleted projects (`POST /v1/projects/{id}/restore`) within 30 days; the worker hard-deletes rows and attachment files after 30 days. Projects soft-deleted during account deletion have no owner left and cannot be restored; the deletion sheet says so.

Deviation from the brief. "Admin may archive if permitted" is a plain yes; there is no per-admin toggle.

### Rationale

A single enforcement function over an enum makes the boundary auditable and lets Phase 2 and Phase 7 tests enumerate every (role x capability) cell. Reserving admin management for the owner closes the hole where any admin could strip the household of every other admin. The database-level single-owner invariant removes the whole class of "last admin" rules. A soft delete with a restore window is cheap insurance on a system with no help desk.

### Rejected alternatives

Multiple owners (ambiguous leave and delete rules); admins able to demote or remove other admins (two admins can lock each other out); viewers allowed to comment (ambiguous read-only); a per-admin archive toggle (a settings matrix nobody asked for); immediate hard delete (irreversible from a phone tap); operator-only recovery of deleted projects (a one-screen restore is cheaper than a support request).

### Consequences

Every service method takes an actor and calls the authorizer; MCP `propose_invite_member` and `propose_remove_member` reuse it. Member rows carry `version`. The client must treat a 404 for a project it was just removed from as "remove from cache" (D12). Realtime handling of `member.role_changed` for self is a Phase 7 test. Account deletion depends on the transfer endpoint.

### Open risks

Household users may find "admin cannot delete the project" surprising; UI copy must say only the owner can. Role escalation through a second account is prevented only by the rule that an invitation never grants a role above the inviter's standing (D04); tests must cover it.

## D04 — Invitation links independent of Apple email matching

### Decision

Token. 32 bytes from the system CSPRNG, base64url without padding (43 characters, 256 bits). The server stores only `SHA-256(token)` as hex in `invitations.token_hash` (unique index); the plaintext exists only in the creation response and the share sheet, and is never logged.

Record. `invitations { id, project_id, role ∈ admin|editor|viewer (never owner; admin only when created by the owner), inviter_id, expires_at, accepted_at, accepted_by_user_id, declined_at, revoked_at, created_at }`. Expiry is chosen at creation from 1, 7 or 30 days (default 7). Single use.

Endpoints. `POST /v1/projects/{id}/invitations {operationId, role, expiresInDays}` → 201 with the invitation (without token), the `url` and the one-time `token`; `GET /v1/projects/{id}/invitations` lists pending invitations without tokens (owner/admin); `DELETE /v1/invitations/{id}` revokes (owner/admin/inviter; strict no-op when already revoked); `POST /v1/invitations/preview {token}` returns `{projectName, inviterDisplayName, role, expiresAt}`; `POST /v1/invitations/accept {operationId, token}`; `POST /v1/invitations/decline {token}` sets `declined_at`. All three token endpoints require a signed-in user. The token travels in the body, never in the path (documented deviation from the brief's `POST /v1/invitations/{token}/accept`).

Link. `https://<host>/invite#<token>`. The token is in the URL fragment, so it never reaches Vapor, tailscale serve, Funnel, cloudflared or any CDN log. The AASA at `/.well-known/apple-app-site-association` claims `/invite` and is served by Vapor with `Content-Type: application/json`. The app also registers `sharedkanban://invite#<token>` and offers a "Join with code" field (project list "+" menu and Settings) that accepts the bare token. The `/invite` page is a single embedded HTML document served by a Vapor route (no FileMiddleware, `Cache-Control: no-store`) that is content-free (no project name, inviter or role): its JavaScript reads `location.hash` and renders an "Open in SharedKanban" button targeting the custom scheme with the fragment, a "Copy code" button, and the TestFlight or App Store link; it never sends the token anywhere. Because the shared link is always https, it is tappable in Messages and Mail in every ingress profile: on the Tailscale beta the page opens in Safari on a tailnet device and hands the token to the app through the button or the code field; once the hostname is public, universal links open the app directly. At Phase 7 the Associated Domains developer mode (`applinks:<host>?mode=developer` with the device's Developer setting) is tried so universal links can work on the household's own devices without a public hostname.

Share. `ShareLink(item: url, subject:, message:)` with the message "<Inviter> invited you to the SharedKanban project “<name>”. Open this link on your iPhone or iPad (expires <date>)". The app keeps a received token in memory only (never Keychain) across the sign-in flow.

Recipient flow. Opening the link launches the app to a "You've been invited" screen; if signed out, Sign in with Apple runs first; then `preview` shows project name, inviter display name, role and expiry with Accept and Decline. Accept lands on the board.

Accept transaction. `SELECT ... FOR UPDATE` on the invitation row, then: unknown token → 404 `not_found`; expired, revoked, already accepted or declined → 410 `invitation_unavailable` with `details.reason ∈ expired|revoked|used|declined`; project soft-deleted → 404; project archived → 410 with reason `project_archived`; the inviter must still be a member whose current role may grant the invited role (owner for admin, owner or admin for editor and viewer) else 410 with reason `inviter_unavailable`; a recipient who is already a member → 200 `{alreadyMember: true}` with the role unchanged, and the invitation is still consumed; otherwise insert the membership, set `accepted_at` and `accepted_by_user_id`, write `member.joined` with `extra {invitationId, inviterUserId}`, and return 201 with the membership. The inviter is notified on accept and on decline (D07). There is no push for a newly created invitation because a link has no known recipient.

Rate limits. preview, accept and decline: 10 per minute per user and 30 per minute per IP (IP limits apply only where the client address reaches the origin, D10); creation: 5 per project per hour.

Tests (Phase 7). Entropy and length, hash-only storage, expiry, replay, revoke-after-share, accept-after-inviter-removal, accept on archived and deleted projects, cross-project token use, already-member consumption.

### Rationale

Sign in with Apple's private relay makes email matching unreliable; a bearer-token invitation bound at acceptance to whoever signed in is the only robust approach. 256 bits make enumeration infeasible; hashing at rest means a database leak yields no usable links; single use with expiry limits a forwarded link. The fragment keeps the secret out of every log at every hop, which path tokens with middleware redaction cannot guarantee. Re-checking the inviter closes the "invited by someone who was later demoted" gap. Always sharing an https link keeps invitations tappable in Messages regardless of ingress profile.

### Rejected alternatives

Email-matched invitations; in-app user search by name (no directory, privacy leak); short numeric codes (brute-forceable); token in the URL path (the brief's shape, rejected for log hygiene); long-lived multi-use links (cannot be revoked per recipient); server-rendered preview pages (would need the token on the server path and an unauthenticated endpoint); distinguishing nothing (a uniform 404) when the holder of a valid token asks why it failed.

### Consequences

Two link handlers in the app share one route parser. The Associated Domains entitlement is a human portal step (D20). The `/invite` page and the AASA are part of the api's routes and tests. Invitations cannot be created or accepted offline (D08). Universal links in production need the public hostname (D10).

### Open risks

Fragment survival in Messages, Mail and Notes link previews must be verified at Phase 7; if any common client strips fragments, the fallback is a path token with redaction at every hop. A user who once chose "Open in Safari" for the host has universal links suppressed by iOS; the in-app code field covers that in production too. Custom URL schemes can be claimed by other apps (negligible for a household).

## D05 — Optimistic concurrency

### Decision

Every mutable record (project, column, task, comment, member) carries `version: Int` (starts at 1, +1 per committed change of that record), `updatedAt` and `updatedBy`. Every version increment is recorded by exactly one activity event carrying that `entity_version` (D17); tests enforce this invariant for every mutation path.

PATCH contract. `PATCH /v1/tasks/{id}`, `/v1/columns/{id}`, `/v1/projects/{id}`, `/v1/comments/{id}` and `/v1/projects/{id}/members/{userId}` require `operationId` and `expectedVersion` in the body (400 `invalid_request` if either is missing). Bodies use the `Patch<T>` wrapper (D22): an absent field means unchanged, an explicit `null` clears. The set of fields present in the body is the "fields in this patch"; field names are the DTO's camelCase names and are the same identifiers used as keys in activity-event `changes`.

Algorithm, inside one transaction that begins with `SELECT ... FOR UPDATE` on the project row (D06):

1. `expectedVersion == current.version` → apply, bump, write the event.
2. `expectedVersion < current.version` → load the events for this entity with `entity_version > expectedVersion` and union their `changes` keys into `changedSinceExpected`. If `changedSinceExpected ∩ fieldsInThisPatch` is empty → apply as a merge: bump, write the event, respond 200 with the response header `X-Merged-From-Version: <expectedVersion>`. If the intersection is non-empty but every intersecting field's incoming value equals the server's current value → drop those fields and proceed as a merge (two people setting the same due date is not a conflict); if nothing is left to change, respond 200 with the current record, no version bump, no event. Otherwise respond 409 `version_conflict`. If the events for the window are missing for any reason, every field is treated as changed (fail closed).
3. `expectedVersion > current.version` → 400 `invalid_request` with `details.reason = "expectedVersionAhead"` and `details.current`; the client reloads the project snapshot.

409 body: `{ "error": { "code": "version_conflict", "message": "Sam changed the notes while you were editing.", "details": { "entityType": "task", "entityId": "...", "expectedVersion": 12, "currentVersion": 14, "conflictingFields": ["notes"], "current": <full current DTO> }, "requestId": "..." } }`. The current DTO is returned only after the normal read authorization for the actor.

Mergeable fields. Task: `title`, `notes`, `dueAt`, `assigneeId` (each independent). `completedAt`, `columnId`, `rank` and `archivedAt` are never PATCHed: position changes go through `/move` (D06), completion is derived from the done column (D19), archive and restore have their own endpoints (D19). Column: `title`, `color`, `wipLimit`, `isDone` (owner/admin); column order goes through `/columns/reorder` with `expectedProjectVersion`. Project: `name`. Comment: `body` only, so concurrent edits of one comment always conflict. Member: `role` only.

Moves. `/move` applies the same rule with the field set `{columnId, rank}`: a stale `expectedTaskVersion` is tolerated when no `task.moved` event exists for the task after `expectedTaskVersion`; otherwise 409 `position_conflict` with the same body shape. Renormalization (D06) does not bump versions and is not a position change.

Validation on every write, merged or not: `assigneeId` must be a current member (422 `validation_failed`); a PATCH on an archived task returns 409 `task_archived` with the current DTO (the client offers Restore); a PATCH on a permanently deleted or unknown entity returns 404; mutations on an archived project return 409 `project_archived`. `updatedBy` is always the actor of the committed write.

Retries. A retry with the same `operationId` replays the stored response, including a stored 409 (D18), so a retry can never double-apply or turn a conflict into a silent success. After the user resolves a conflict the client submits a new operationId with the new `expectedVersion`.

### Rationale

Field-level merge removes almost every 409 a household will see (one person renames while the other sets a date) while keeping the same-field case explicit, exactly as the brief asks, without a CRDT. The activity log already records changed fields per version, so no per-field version columns are needed, and because events are retained forever (D17) the merge window never expires. Treating identical values as non-conflicts avoids the most common spurious conflict. Keeping derived and position fields out of PATCH makes the move endpoint the single serialization point the brief wants.

### Rejected alternatives

Last-writer-wins (silent loss, forbidden by the brief); rejecting any stale version (spurious conflicts for two people on one card); per-field version counters (more columns, same result); CRDT or OT for notes (unjustified at this scale); comparing `updatedAt` instead of versions (clock skew); 409 for `expectedVersion` ahead of current (it is not a conflict, it is a client that needs a resync).

### Consequences

Every mutation path must write complete `changes` keys or merges silently degrade into conflicts for those fields; the one-event-per-version test guards this. SharedDTOs defines `Patch<T>` and the error details shape. The client conflict UI (D08) relies on `details.current` and `conflictingFields`. The move endpoint and the PATCH endpoint share one `ConcurrencyGate` implementation.

### Open risks

Clients offline longer than 30 days (D08 age-out) never replay, so they never hit stale merges, but a device restored from an old snapshot could send very old versions; the fail-closed rule handles it. Comment bodies are single-field, so concurrent comment edits always conflict (acceptable).

## D06 — Card ranking and move contract

### Decision

Rank representation. `tasks.rank TEXT NOT NULL COLLATE "C"` and `columns.rank` likewise, holding fractional-indexing keys over the alphabet `0-9A-Za-z` (62 symbols) generated by `RankKey.generateKeyBetween(_ a: String?, _ b: String?)` and `RankKey.generateNKeysBetween(_ a:, _ b:, n:)` implemented once in SharedDTOs and unit-tested on Linux and iOS; keys never end in the smallest symbol, so insertion between any two keys always succeeds and keys grow by roughly one character per repeated insertion at the same spot. A partial unique index on `tasks (column_id, rank) WHERE archived_at IS NULL` guards active tasks. Every client sort uses byte-wise comparison (`SortDescriptor(\.rank, comparator: .lexical)` or UTF-8 comparison), never locale-aware string comparison, then `id` as the tiebreaker.

Renormalization. Trigger: the generated key is longer than 32 characters. Scope: the destination column only, inside the same transaction: every active task in the column, in current order with the moving task at its new place, receives keys from `generateNKeysBetween(nil, nil, n)`. Because a partial unique index cannot be deferred, the update is two-pass: pass one prefixes every rank in the column with `-` (outside the alphabet, so no final key collides), pass two assigns the final keys. Renormalization rewrites rank only; it does not bump task versions, and it writes one `column.ranks_normalized` event with `extra.ranks = [{taskId, rank}]` after the `task.moved` event so other clients update without a snapshot (clients apply events in sequence order without version gating, D08).

Move request. `POST /v1/tasks/{taskId}/move` with body `{ operationId, destinationColumnId, beforeTaskId | null, afterTaskId | null, expectedTaskVersion }`. `afterTaskId` names the card that will be immediately above (precede) the moved card; `beforeTaskId` names the card immediately below (follow). Both null → append to the bottom. This naming is stated in bold in `docs/api.md` because it is easily inverted.

Server algorithm, under `SELECT ... FOR UPDATE` on the project row (every project-scoped mutation takes this lock first, which serializes writes per project, allocates the sequence under the same lock, and makes deadlocks impossible):

1. Authorize `moveTask` (D03); the project must not be archived.
2. The task must be active (archived → 409 `task_archived`). The destination column must be an active column of the task's own project (otherwise 404 `not_found`; a column id from another project is never acknowledged). Neither neighbor may be the moving task itself (422 `validation_failed`).
3. Resolve neighbors: a neighbor id that belongs to another project → 404. Both neighbors present, active and in the destination column but no longer adjacent → place immediately after `afterTaskId` (or immediately before `beforeTaskId` when `afterTaskId` is null). Exactly one neighbor missing (archived, moved elsewhere, deleted) → use the other. Both missing → 409 `neighbors_changed` with `details.currentOrder = [taskIds]` of the destination column. Adjacency is not required, so concurrent inserts into one gap both succeed in deterministic order.
4. Apply the D05 version rule for the field set `{columnId, rank}` → possibly 409 `position_conflict`.
5. Compute the key, renormalize if needed, set `completedAt = now()` when entering the `is_done` column and `null` when leaving it (D19), bump `task.version`, write `task.moved` with `changes {columnId, rank, completedAt?}` and `extra {fromColumnId, toColumnId, wipExceeded, completionChange ∈ completed|reopened|null}`, then the optional `column.ranks_normalized` event, and the operation record (D18).

Response 200: `{ "task": TaskDTO, "renormalizedRanks": [{ "taskId", "rank" }] | null, "sequence": <sequence of the task.moved event> }`.

Creation and restore placement. A new task is appended to the bottom of its column; a task created offline is appended to the bottom of the column at replay time; a restored task returns to the bottom of its column, or of the first column when its column is archived (D19).

Column order uses the same keys; `POST /v1/projects/{id}/columns/reorder {operationId, orderedColumnIds, expectedProjectVersion}` reassigns all column ranks with `generateNKeysBetween` and writes one `column.reordered` event with `extra.orderedColumnIds`.

Tests (Phase 2): same-card concurrent moves, two cards into the same gap, one neighbor gone, both neighbors gone, cross-project neighbor and column ids, self as neighbor, 1,000 insertions into one gap triggering renormalization, replay with the same operationId, byte-order sorting of keys such as `a9` and `a10` on both platforms.

### Rationale

String ranks never exhaust precision the way doubles do (about 50 midpoint insertions) and sort natively in PostgreSQL under the `C` collation; implementing the generator once in SharedDTOs lets the client place a card optimistically with the same key the server will accept. Neighbor-based moves make retries safe and avoid clients sending absolute positions, as the brief requires, and tolerant neighbor resolution avoids the spurious snap-back a strict adjacency check would show during ordinary concurrent use. Locking the project row is already required for sequence allocation, so using it as the single lock buys serialization for free.

### Rejected alternatives

Double or decimal ranks (precision exhaustion, fragile equality); integer positions with shifting (O(n) updates, lost-update races); client-set ranks (collisions); strict neighbor adjacency with 409 (rejects legitimate concurrent moves); column-row lock ordering (buys nothing once the project row is locked); integer midpoint ranks (sound, but renormalizes far more often and still needs the same event plumbing).

### Consequences

The server package depends on SharedDTOs for the generator. The client must handle `neighbors_changed` by re-reading `currentOrder` and retrying once with new neighbors and a new operationId, then snapping to the server state. Write throughput is serialized per project (documented as a known limit, fine for a household). Verify that `COLLATE "C"` is byte-wise on the pinned PostgreSQL major at Phase 2.

### Open risks

A "move to top" habit grows keys faster and triggers renormalization more often; harmless but covered by the 500-move test. The two-pass renormalization and the savepoint-based idempotency record (D18) must be expressible through Fluent plus raw SQLKit; verify at Phase 2.

## D07 — Local versus remote notifications

### Decision

Rule. Notifications caused by time are local; notifications caused by another person are remote through APNs. Due-soon and overdue reminders are local-only in release 1, a documented deviation from Prompt 8's worker list: the worker never pushes due events, which avoids cross-device duplicates and time-zone bookkeeping on the server.

Local. Scheduled on-device with `UNCalendarNotificationTrigger` (DST-safe) from cached data for tasks that are assigned to the signed-in user, plus unassigned tasks they created, that are not completed or archived. Two requests per task with identifiers `due:<taskId>:soon` (at `dueAt` minus the lead time) and `due:<taskId>:now` (at `dueAt`); overdue is a UI treatment and fires no repeated reminders. Lead time is a per-account setting: none, 1 hour, 1 day (default 1 day). `dueAt` is an instant; the date picker defaults to 09:00 local when the user picks only a day; there is no all-day concept in release 1. At most 50 pending requests (nearest due dates first) under the 64-request system cap. Rescheduled after every sync, on app foreground, on time-zone change, after a push is received or tapped, and from a `BGAppRefreshTask` (best effort). During quiet hours local reminders are shifted to the end of the window.

Remote categories (the worker derives each push from exactly one activity event): `invitation` (your invitation was accepted or declined → inviter; a member joined → owner and admins); `assignment` (assigned or unassigned by someone else); `comment` (a comment on a task you created, are assigned to, or have commented on); `mention` (you are in `mentionedUserIds` of a comment, validated as project members when the comment is created; no display-name parsing); `membership` (your role changed, you were removed, ownership transferred to you; owners and admins: member left or removed); `activity` (task created, moved or archived, column changes; default off, per-project opt-in, collapsed with `apns-collapse-id = project:<id>` and throttled to one push per project per 5 minutes). The actor never receives a push for their own event. There is no app badge in release 1.

Settings. Account-level: category toggles (invitation, assignment, comment, mention, membership on; activity off), `dueLeadTime`, quiet hours `{start, end}` with the device's IANA time zone sent in the device record. Per-project on the membership: `notificationSettings { muted, overrides: {category: Bool} }`; mute suppresses every remote category except `membership` events about yourself. Quiet hours: the worker still sends but with `interruption-level: passive` so items land in Notification Center without alerting; no server-side deferral queue.

Dedup and delivery. Outbox table `notification_deliveries { event_id, user_id, category, state ∈ queued|sent|failed, attempts, created_at, sent_at }` unique on `(event_id, user_id)`; the worker reads events through per-project cursors (D17), inserts deliveries, and sends with `FOR UPDATE SKIP LOCKED`, so restarts cannot duplicate. `apns-collapse-id = task:<taskId>` for comment pushes, `project:<id>` for activity, none for mention, assignment, invitation and membership. Token-based APNs authentication (.p8 over HTTP/2) through a `PushProvider` protocol with a fake in tests.

Payload. `{ aps: { alert: {title, body}, sound: "default", thread-id: <projectId>, category }, sk: { type, projectId, taskId?, commentId?, sequence } }`; the body is the task title plus at most 80 characters of comment text; no notes, tokens or emails. The iOS system "Show Previews" setting governs lock-screen exposure; the app adds no second toggle.

Deep links. The app resolves `projectId/taskId` with its own session after syncing; 403 or 404 shows "No longer available" and payload content is never trusted.

Devices. `PUT /v1/devices/{installationId} { apnsToken, environment ∈ sandbox|production, timeZone }` on every launch when anything changed (idempotent full replacement); environment follows the build configuration (sandbox for Debug, production for TestFlight and App Store). APNs 410 or `BadDeviceToken` marks the device inactive; device rows reference the session and are deleted on logout and on every session revocation, including reuse detection.

Authorization prompt. Requested at the first moment a notification could be useful (joining or creating a shared project, setting a due date, or sharing an invitation), never on first launch, with a one-sentence pre-prompt; provisional authorization is not used.

### Rationale

Due dates are personal and deterministic, so the device is the right scheduler and reminders keep working offline; everything that needs another person's action goes through the worker from the event log it already has. The outbox with a unique key is what makes "exactly once per user per event" boring to operate. Passive delivery during quiet hours is simpler and safer than queuing. Explicit `mentionedUserIds` removes fuzzy name parsing.

### Rejected alternatives

Server-scheduled due reminders (per-user time-zone scheduling, cross-device duplicates); silent background pushes to refresh the board (unreliable, battery cost); server-side deferral and coalescing during quiet hours (extra state for little value); badge counts (unread state per user per project); email digests (deferred by the brief).

### Consequences

The worker needs device time zones, quiet-hour windows and membership settings. The app needs an idempotent reminder scheduler driven by the cache. The APNs .p8 key is a one-time human portal step (D20). Phase 8's fake push provider asserts collapse ids, dedup keys and the actor exclusion.

### Open risks

Local reminders only fire on devices that have synced the task; a second device never opened gets none (accepted and documented). `BGAppRefreshTask` is unreliable, which is why foreground sync and push receipt also reschedule. How Focus modes treat passive-level pushes must be verified at Phase 8.

## D08 — Offline cache and conflict behavior

### Decision

Cached per device (D12): the project list; for every project opened in the last 30 days: columns, active tasks, members, the last 200 activity events, attachment metadata, comments for tasks that were opened, and `SyncState { projectId, lastSequence, snapshotAt }`. Archived tasks are fetched on demand and cached once viewed. Attachment bytes and thumbnails live in a 200 MB LRU on-disk cache under Caches, never in SwiftData.

Outbox. `PendingOperation { id (= operationId, UUID v4, minted when the operation is created, not when sent), createdAt, kind, projectId, entityId, dependsOn (operation id, optional), method, path, body JSON, requestVersion, expectedVersion, attempts, state ∈ pending|inFlight|conflict|failed, lastErrorCode }` in the durable `outbox.store`. Clients generate entity ids for tasks, comments, columns and projects at creation time (the server accepts client ids with ownership and uniqueness validation; collision → 409 `duplicate_id`), so there is no temporary-id mapping and a create-then-edit chain replays naturally.

Allowed offline: create, edit, move, archive and restore tasks; comments; due date and assignee changes; column rename, color and WIP changes. Not allowed offline (control disabled with a footnote, nothing queued): project creation and deletion, column add, archive and reorder, invitations, role changes, removals, ownership transfer, account deletion, attachment upload (a file picked offline is staged locally as "waiting to upload" and its background PUT starts when online).

Replay. Strict global FIFO by `createdAt`, one operation in flight at a time, only after the session is valid and reachability returns. 5xx, network errors and 429 retry the head with exponential backoff 1 s doubling to 60 s with ±20 % jitter, without an attempt limit while the app lives. 409 (`version_conflict`, `position_conflict`, `neighbors_changed`, `task_archived`) marks the operation `conflict`, removes it from the head, and blocks later operations on the same `entityId` (and any operation whose `dependsOn` chain reaches it) while others continue. 400, 403, 404, 410, 422 (`not_found` for a project the user was removed from, `project_archived`, a rejected create, a validation failure) mark the operation `failed` with a user-visible reason, and every dependent operation fails with it. Operations older than 30 days are moved to `failed` ("too old to apply"), matching the idempotency TTL (D18). An operation left `inFlight` by an app kill is retried on the next launch with the same operationId, which is exactly the replay case D18 covers.

Reconnect order: (1) refresh the session if needed (D16); (2) catch up: if `SyncState` exists and is younger than 24 h, `GET /v1/projects/{id}/events?after=<lastSequence>&limit=500` until caught up, applying events in sequence order; otherwise, and on 410 `sequence_too_old`, reload the snapshot `GET /v1/projects/{id}` which replaces the project subtree and carries the current `sequence`; (3) replay the outbox; (4) subscribe on the WebSocket (D13). Live events are applied only when `sequence == lastSequence + 1`; any gap triggers step 2. Events and snapshots are applied without version gating because sequence order is total per project.

Draft overlay. While a pending operation exists for an entity, the cache row keeps `draftTitle`, `draftNotes`, `draftDueAt`, `draftAssigneeId`, `draftColumnId`, `draftRank` and `hasPendingOperation`; views render the draft over the server fields, so an incoming event for the same entity updates the server fields without erasing what the user sees. The overlay is cleared when the operation succeeds or is discarded.

Conflict UX. The card shows a small warning glyph; the task detail shows a banner "Changed by <name> <relative time>" with Keep Mine (resubmit with the current version under a new operationId), Use Server (discard the draft), and, for notes only, Compare (server and local text side by side, stacked in compact width, local text editable, Save submits a new operation). `task_archived` offers Restore and apply, or discard. Rejected moves show no dialog: the card snaps to the server position with the D01 banner. Entities deleted on the server (404) drop the local change with a toast.

Status. An "Offline, 3 changes waiting" capsule under the navigation title while offline or while the outbox is non-empty; pending cards show a clock glyph with the VoiceOver value "waiting to sync". Logout warns when the outbox is non-empty and offers to wait for sync. On a forced sign-out (401 `session_revoked`, refresh reuse, "sign out everywhere" from another device) the app keeps both stores, shows the sign-in screen, and resumes the outbox if the same user signs back in; a different user wipes both stores. Account deletion wipes both stores.

Explicitly not promised: automatic text merging, offline membership changes, offline attachment uploads completing without the app being launched again, conflict dialogs for moves, cross-device consistency of unsent drafts, and preservation of pending operations if the outbox store itself is corrupt (it is in its own store to make that rare).

### Rationale

Preserve edits, surface conflicts, never silently drop is exactly the brief's bar. Client-generated ids and a dumb FIFO outbox remove the hardest parts of offline sync; per-entity blocking keeps the rest of the board flowing after one conflict; `dependsOn` makes a rejected create fail its edits visibly. The draft overlay is the only design that keeps the user's edit visible when a server event for the same entity arrives. Keeping membership and destructive operations online-only avoids queued security-relevant actions executing minutes later under changed permissions. Aligning age-out with the idempotency TTL means a replay is always protected against duplicates.

### Rejected alternatives

Per-project queues (reorder cross-project edits for little gain); automatic three-way text merge (silent wrong merges); CRDT notes; version-gated event application (loses renormalized ranks and other non-versioned updates); discarding pending operations on conflict; wiping the outbox on every forced sign-out (a security event would destroy unsynced edits).

### Consequences

The server accepts client-supplied ids on create. Idempotency records last 30 days (D18). UI needs explicit states: queued, syncing, conflict, failed, offline read-only for archived projects. The overlay-aware fetch is the most intricate client code; Phase 5 tests must cover "server event arrives for an entity with a pending draft", dependent failure, replay order, and inFlight recovery after a kill.

### Open risks

A device offline for more than 30 days loses queued edits (surfaced as failed, not silently). Conflicts on the same field edited offline by both people must be exercised in the two-device manual scenario. SwiftData multi-store configuration on the minimum OS is verified at Phase 5.

## D09 — Account deletion and token revocation

### Decision

Flow. Settings → Account → Delete Account opens a consequences sheet: what is deleted, what remains in shared projects (comments, attachments, tasks and activity attributed to "Deleted member"), that Sign in with Apple authorization is revoked, and a list of every owned project; for each owned project that has other members the user must choose Transfer to <member picker> or Delete project; owned projects without other members are listed as "will be deleted permanently" (no restore, D03). Continue → `confirmationDialog` with a destructive Delete button → the app calls `POST /v1/account/delete-challenge` → `{nonce, expiresAt (+5 minutes)}` → runs a fresh Sign in with Apple request with that nonce → `POST /v1/account/delete { identityToken, authorizationCode, nonce, transfers: [{projectId, newOwnerUserId}], deletions: [projectId] }`. (The brief's `DELETE /v1/account` is realized as a POST because D18 forbids bodies on DELETE.) If the user cancels the Apple sheet, the app explains that deletion requires it and stops.

Server. Verify the identity token (signature, issuer, audience, expiry), require `nonce` to equal an unconsumed challenge issued to this user within 5 minutes, `sub` to equal the user's Apple subject, and `iat` within the last 5 minutes; consume the challenge (single use), otherwise 401 `reauth_required`. Validate that every transfer target is a current member and that every owned project with other members appears in `transfers` or `deletions`, else 409 `owned_projects_require_transfer` with `details.projects: [{id, name, memberCount}]`. Then in one transaction: apply transfers through the D03 transfer path (previous owner becomes admin, then their membership is deleted); soft-delete the chosen and solo-owned projects (purged by the worker after 30 days, no restore); revoke every session and delete device rows (D16), invalidate outstanding upload tokens (D14) and Claude connection grants and pending AI changes (D15); delete pending invitations the user created; delete every membership, clearing `assigneeId` on that user's tasks in shared projects with `task.updated` events `via = system` and writing `member.left`; anonymize the user row in place: `apple_subject = NULL`, `email = NULL`, `display_name = 'Deleted member'`, `apple_refresh_token_ciphertext = NULL`, `deleted_at = now()`; keep the row forever as the foreign-key target; write an audit row. Response 204.

Apple revocation. At sign-in the server stores Apple's refresh token from the first code exchange, encrypted with AES-GCM under `APPLE_TOKEN_KEY` (32 bytes from the environment). At deletion it exchanges the fresh authorization code and calls `POST https://appleid.apple.com/auth/revoke` with the fresh token (TN3194 style), falling back to the stored token; failure never blocks deletion: a worker retry record runs hourly for 7 days and logs the final outcome. `POST /v1/auth/apple/notifications` implements Apple's server-to-server events (`consent-revoked`, `account-delete`): revoke all sessions and set `users.apple_revoked_at`; the next launch shows "Sign in again to continue". The endpoint is registered in the developer portal only once a public hostname exists (D10); it is harmless until then. On launch the app calls `ASAuthorizationAppleIDProvider.getCredentialState`; `.revoked` or `.notFound` signs out locally and calls logout.

Client. After 204 the app wipes Keychain, both SwiftData stores, the attachment cache, pending local notifications and the APNs registration, and shows the sign-in screen with a one-time confirmation. A non-empty outbox is shown in the consequences sheet as "N unsynced changes will be discarded". A later Sign in with Apple with the same subject creates a brand-new user. The MCP audit log rows of the deleted user are kept for 1 year (D15). Timing: immediate, synchronous, irreversible; no grace period for the account.

Tests (Phase 3): deletion with and without owned shared projects, challenge replay, stale identity token, wrong subject, Apple revoke failure path, deleted user's token use → 401, re-sign-in after deletion, the second member seeing `member.left` and the display name change.

### Rationale

App Store rules require in-app deletion and TN3194 recommends revoking tokens with a fresh code; a fresh Apple sign-in bound to a server-issued single-use challenge means a stolen access token cannot delete the account. Deciding every owned project in one request makes the whole deletion one transaction instead of a bounce-and-retry loop. An anonymized tombstone row preserves the other household member's board history and referential integrity. Encrypting the stored Apple refresh token costs one environment key and keeps a database dump from yielding revocable credentials.

### Rejected alternatives

Hard-deleting the user row with cascades (destroys the household's shared history); "deactivate" with a later purge (users expect immediate deletion); a typed passphrase or bare `{confirm: "DELETE"}` body (a stolen bearer token would suffice); storing Apple's refresh token in plaintext; refusing deletion while projects are owned (violates the requirement).

### Consequences

Sign-in must persist the encrypted Apple refresh token from Phase 3. The transfer endpoint from D03 is on the critical path. The privacy inventory states what remains after deletion. Display-name lookups must handle tombstones everywhere, and names are resolved at render time (D17).

### Open risks

Apple's revoke endpoint behavior, the `client_secret` JWT format signed with the Sign in with Apple key, and the server-to-server notification configuration must be verified against current documentation at Phase 3. Apple may reject an old stored refresh token; best effort plus retry is the honest ceiling.

## D10 — Local versus Apple versus secure ingress; ingress profile order; ATS

### Decision

Stays on the Mac mini: API, WebSocket hub, worker, PostgreSQL, attachment files, MCP endpoint and stdio bridge, backups, logs, sessions and idempotency state. Necessarily touches Apple, outbound HTTPS only: Sign in with Apple (JWKS from `appleid.apple.com` cached 24 h, code exchange and revoke at `/auth/token` and `/auth/revoke`), APNs (`api.push.apple.com`, `api.sandbox.push.apple.com`), App Store Connect and TestFlight for distribution, and Apple's CDN fetching the AASA once universal links are enabled. The `api` and `worker` containers get an egress allowlist of exactly those Apple hosts (best effort through Docker network policy; the threat model does not rely on it).

Ingress profiles, in order:

1. LAN development. Debug builds only: `http://<mac-mini>.local:8080`; the Debug Info.plist sets `NSAllowsLocalNetworking = true` and `NSLocalNetworkUsageDescription`; Release builds carry no ATS exceptions. The Compose `dev` profile publishes the api on the LAN interface; every other profile publishes `127.0.0.1:8080` only.
2. Private household profile — the release-1 production profile. Tailscale on the Mac mini and on both phones (iPhone and iPad on-demand VPN enabled; documented interaction with other VPN profiles and iCloud Private Relay). `tailscale serve` terminates TLS with a Let's Encrypt certificate for `<mini>.<tailnet>.ts.net` (HTTPS certificates enabled once in the admin console) and proxies to `127.0.0.1:8080`. Nothing listens on the public internet; no domain, no certificate work, no ATS exceptions; invitations work through the https link, the `/invite` page and the code field (D04).
3. Public HTTPS, enabled only when a concrete need appears (remote MCP from claude.ai or a phone, universal links, or a device that cannot run Tailscale). Default: Tailscale Funnel on the same hostname (one admin-console toggle, no new accounts, TLS still terminates on the Mac mini), restricted with `tailscale funnel` path scoping to `/v1/*`, `/invite`, `/.well-known/*`, `/health` and, after Phase 9b ships OAuth, `/mcp`. Documented alternative: Cloudflare Tunnel with an owned domain and `cloudflared` in Compose, with the explicit note that Cloudflare decrypts traffic at its edge and that forwarded client-IP headers are trusted only for requests arriving from the tunnel.

Non-negotiables in every profile: a tunnel is transport, not authorization; every REST request, WebSocket upgrade and MCP call carries a SharedKanban bearer token and passes project authorization (D03, D16); no IP- or tailnet-based allowlists are relied on; PostgreSQL has no published port; rate limits (D22) are keyed by user first and by client IP only where the address reaches the origin; HSTS and `X-Content-Type-Options: nosniff` on every response. The base URL and environment name are injected through a git-ignored `Config/Environment.xcconfig` (an example file is committed) plus a Debug-only in-app environment picker; the production hostname never enters source control. Tailscale key expiry is disabled for the Mac mini node in the admin console (one-time human click) so the server never silently needs re-authentication. The Tailscale build used on the Mac mini is the one whose CLI supports `serve`, `cert` and `funnel` (verify which macOS variant at Phase 10). The runbook contains the "switch to public" steps.

### Rationale

For two people who will both install Tailscale anyway, the private profile is the least human work possible and the smallest attack surface: no domain, no Cloudflare account, no reverse proxy container, and a loopback-only API that a misconfigured firewall cannot expose. Funnel reuses the same tool when public access is actually needed and keeps TLS end-to-end to the mini, which is the better privacy posture for a home server.

### Rejected alternatives

Public ingress as the default (domain, account and more human steps for no household benefit); port forwarding on the home router (inbound exposure, dynamic IP); self-signed certificates with ATS exceptions (weakens ATS for the whole app); Cloudflare Access service tokens in the app (a shippable secret); a Caddy reverse proxy in front of the API (tailscale serve already terminates TLS; a second terminator would be redundant).

### Consequences

The AASA and the Associated Domains entitlement use the `*.ts.net` hostname. The `/mcp` endpoint is loopback-only until Phase 9b. The threat model lists Tailscale account compromise and the Funnel endpoint as public internet. The phone-side VPN requirement affects first-run UX and must be documented ("the app needs the Tailscale VPN to be on").

### Open risks

Funnel WebSocket support, idle timeouts, bandwidth limits, client-IP forwarding and the free-plan limits must be verified at Phase 10. Cloudflare's free-tier body and WebSocket limits are re-checked only if that alternative is chosen. Universal links in production need the public hostname; the developer-mode experiment in D04 may remove that dependency for the household's own devices.

## D11 — Backend stack and runtime

Expanded in ADR-0001 (`docs/decisions/0001-vapor-fluent-postgresql.md`).

### Decision

Toolchain and libraries. Swift 6 language mode with `-strict-concurrency=complete` on the latest stable Swift 6.x toolchain available at Phase 1, the same version on Linux and on the Mac mini (verify the exact minor). If the chosen Vapor release is not clean under Swift 6 mode, the server package pins Swift 5 language mode and an ADR records it. Vapor 4.x latest (if Vapor 5 has a stable release at Phase 1, evaluate it once and record an ADR; never start on a pre-release); Fluent 4 with `fluent-postgres-driver` on PostgresNIO; JWTKit 5 for Apple identity-token verification; APNSwift for token-based APNs (fallback: a thin AsyncHTTPClient HTTP/2 client); swift-log with a JSON handler that redacts tokens and paths; swift-crypto. No other server dependency without an ADR. `Package.swift` uses `from:` minimums and the committed `Package.resolved` pins exact versions, recorded in `docs/architecture.md` at Phase 1. PostgreSQL major 17 pinned by image tag (`postgres:17-alpine`; verify at Phase 1 whether a newer major is the better pin for the life of release 1; stay on one major).

Queues. No Redis and no Vapor Queues: PostgreSQL tables are the only queue. The worker polls `projects.last_sequence` against per-project cursors every 2 s for notifications (D17), uses `FOR UPDATE SKIP LOCKED` on the delivery outbox, and runs hourly and daily maintenance timers. LISTEN/NOTIFY is not used in release 1 (the worker never publishes realtime events, D13).

One binary. The executable `Run` has subcommands: `serve` (API, WebSocket hub, MCP endpoint), `worker` (APNs outbox, orphan and attachment cleanup, project purge, Apple revoke retries, session and operation purges, backup status), `migrate` (explicit deploy step, never auto-run on `serve`), `mcp-stdio` (the stdio bridge, D15), `mcp-token` (create, list, revoke Claude connection tokens), `admin` (owner-only maintenance such as `sessions revoke-all`, `status`). Health: `GET /health` (process up) and `GET /ready` (database reachable, migrations current, last backup age).

Compose. Services: `api` (publishes `127.0.0.1:8080`; the `dev` profile publishes on the LAN), `worker`, `postgres` (internal network only, named volume; `127.0.0.1:5432` published only under the `dev` profile), `migrate` (one-shot, run explicitly with `docker compose run --rm migrate`, not in `depends_on`). Tailscale, backups (D21) and the stdio bridge run on the macOS host. Configuration comes exclusively from environment variables loaded from `/Users/kanban/SharedKanban/secrets/.env` outside the repository (`.env.example` committed). Writable host data lives under `/Users/kanban/SharedKanban/data/{attachments,backups}` and is bind-mounted into `api` and `worker` (Docker Desktop shares `/Users` by default; performance is adequate for 25 MB files). Images: multi-stage build from the official `swift:6.x` builder to a slim runtime, non-root user, read-only root filesystem, writable mounts only for attachments and `/tmp`, health checks, restart policies, graceful shutdown.

Runtime on macOS. Docker Desktop (OrbStack documented as the lighter alternative) running under a dedicated auto-login service user `kanban` (see D21 for the FileVault consequence). Escape hatch: `deploy/launchd/` plists plus `deploy/launchd/build.sh` build the arm64 release binary with `swift build -c release` and run `serve` and `worker` as LaunchDaemons against Homebrew `postgresql@17` with identical environment variables; this path needs no GUI login and is exercised once in Phase 10 so it is known to work before it is needed.

### Rationale

The brief fixes Swift, Vapor, Fluent and PostgreSQL; pinning one PostgreSQL major and one toolchain minimizes surprise upgrades on a machine nobody babysits. PostgreSQL-as-queue and one binary with subcommands remove two services and keep worker and API code paths identical, which also makes the launchd fallback trivial. Explicit migrations prevent an unattended container restart from mutating the schema; a one-shot service wired into `depends_on` would be auto-migration in practice.

### Rejected alternatives

Separate worker package (duplicate models and migrations); Redis or Vapor Queues (another service); Hummingbird (the brief chose Vapor); auto-migrate on boot (dangerous with restores and rollbacks); a Caddy or backup container (no TLS terminator is needed behind tailscale serve, and backups run from host launchd so they reach the SSD and iCloud Drive natively); running PostgreSQL natively by default (Compose keeps dev, test and restore drills reproducible).

### Consequences

Phase 1 must prove the Linux container can run `swift test` for `server/` and `shared/` against a local PostgreSQL. Docker Desktop's first launch needs GUI acceptance by the human (D20). Strict concurrency requires `Sendable` DTOs from the start. Bind-mounted paths must stay under `/Users` to avoid Docker file-sharing configuration.

### Open risks

Vapor 5 timing, APNSwift maintenance status and Swift 6 cleanliness of the chosen Vapor release are checked at Phase 1. Docker Desktop stability after macOS updates and its memory use on a small Mac mini may push production toward the launchd path.

## D12 — SwiftData as offline cache only

Expanded in ADR-0002 (`docs/decisions/0002-swiftdata-as-cache.md`).

### Decision

Two `ModelContainer`s with separate store files in Application Support: `cache.store` (disposable) with `CachedProject`, `CachedColumn`, `CachedTask`, `CachedMember`, `CachedUser`, `CachedComment`, `CachedAttachment`, `CachedActivityEvent`, `SyncState`; and `outbox.store` (durable) with `PendingOperation` (D08) and `StagedUpload` (D14). Transport DTOs live in the SharedDTOs package as plain `Codable` structs with no SwiftData import; `@Model` classes exist only in the iOS target, are never `Codable` for transport, and never cross the APIClient boundary. `CachedTask` carries the server fields plus the draft overlay fields and `hasPendingOperation` (D08).

Mapping and access. One explicit mapping file per entity: `CachedTask.apply(_ dto: TaskDTO)` (upsert by `#Unique([\.id])`, overwrite every server-owned field, leave draft fields untouched) and `CachedTask.toDTO()` used only to build requests. A `ProjectRepository` protocol separates views from storage and transport, with the live SwiftData implementation and an in-memory fake used by previews, unit tests and the Phase 4 prototype. All writes happen inside `SyncEngine`, a single `@ModelActor`; views read through `@Query` on the main context sorted by `(rank, id)` with `comparator: .lexical`, or through `@Observable` view models that never hold `@Model` instances across actors (Swift 6 strict concurrency). The outbox container is not placed in the SwiftUI environment; only `SyncEngine` touches it and publishes an `@Observable SyncStatus` (pending count, offline, reconnecting) for views. An optimistic edit mutates the cache row's draft fields and enqueues the `PendingOperation` in the same save.

Invalidation. The server is always right: events are applied in sequence order and snapshots replace the project subtree in one transaction (upsert by id, delete rows missing from the snapshot); a `member.removed` event for self, a 403 or 404 on a project fetch, or a `project.deleted` event removes that project's subtree immediately; projects not opened for 30 days are evicted by a maintenance pass; the project list shows "Updated N min ago" while a background refresh runs. Snapshot reload happens on 410 `sequence_too_old`, on `SyncState` older than 24 h, and on pull to refresh.

Schema stance. `cache.store` has no migration path: a `CacheSchema.version` string recorded in the store's metadata is compared at launch; on mismatch the store file is deleted and projects are re-fetched (no SwiftData migration code is ever written for the cache). `outbox.store` uses a `VersionedSchema` with lightweight, additive-only migrations; if a lightweight migration fails, the pending operations are exported to `Application Support/unsynced-operations.json`, surfaced as "unsynced changes", and the store is recreated; each `PendingOperation` carries `requestVersion` so an app update never replays a stale request shape (a mismatch fails that operation visibly). Logout wipes both stores (after the D08 warning); a forced sign-out keeps them (D08); account deletion wipes both.

Files. After creation both store files, the staged upload directory and the attachment cache are set to `FileProtectionType.completeUntilFirstUserAuthentication` (required for background uploads and launch-time sync) and are marked `isExcludedFromBackup = true` (they hold other members' data and unsent drafts, and a restored device starts at sign-in anyway because Keychain items are this-device-only). Keychain items that survive an app uninstall are detected by a first-launch flag in UserDefaults and wiped.

### Rationale

SwiftData is excellent as a query layer for views and poor as a long-lived schema contract; treating the cache as disposable removes the entire migration risk class. Separating the outbox protects unsynced edits from cache resets. The repository seam is what Prompts 4 and 5 require for previews and tests. DTOs isolated from SwiftData keep the Linux-tested contract pure.

### Rejected alternatives

SwiftData models as DTOs (couples schema to wire format, breaks Linux tests); Core Data (more code, no benefit); GRDB or a hand-rolled SQLite cache (third-party or more code for the same disposable cache); one container for both stores (a cache wipe would lose unsent edits); CloudKit mirroring (violates server-authoritative Mac mini hosting).

### Consequences

Every DTO change needs a mapping update and a `CacheSchema.version` bump. Views must tolerate an empty cache while a snapshot loads. Pending operations reference entity ids, not cache objects, so they survive cache wipes. Test targets use `isStoredInMemoryOnly` containers.

### Open risks

`@Query` performance with about 1,000 tasks per project is measured at Phase 11. `#Unique` and `#Index` require the iOS 18 SwiftData; if D20's minimum ever drops, upserts become manual. `ModelActor` behavior and the two-container setup on the minimum OS are verified at Phase 5.

## D13 — WebSockets for realtime

Expanded in ADR-0003 (`docs/decisions/0003-websockets-realtime.md`).

### Decision

Endpoint and authentication. `WSS /v1/realtime` on the same origin as REST, upgraded through tailscale serve or Funnel. The access token travels in the `Authorization: Bearer` header of the upgrade request (URLSessionWebSocketTask accepts custom headers); never in the query string. An invalid or expired token is rejected with HTTP 401 before the upgrade. A socket may outlive its access token: the hub keys every connection by session id, every revocation path (logout, per-session revoke, revoke-all, refresh reuse, account deletion, absolute session expiry) closes that session's sockets with close code 4401 `session_revoked`, and the hub additionally re-validates every open socket's session against the database every 60 s so revocations performed by the `admin` subcommand take effect within a minute. At most 3 sockets per session and 20 project subscriptions per socket.

Protocol (JSON, one object per text frame, `type` field). Client → server: `subscribe {projectId}`, `unsubscribe {projectId}`, `ping`. Server → client: `subscribed {projectId, sequence}` after the membership check, `event {projectId, sequence, event: ActivityEventDTO}` for every committed event, `unsubscribed {projectId, reason ∈ membership_revoked|project_unavailable}`, `error {code, projectId?}` (a subscribe to a project the user is not a member of answers `not_found`, never `forbidden`, so existence does not leak), `pong`. Inbound limits: 10 messages per second and 64 KB per frame; exceeding them closes with 4429. The protocol is versioned with the REST path (`/v1/realtime`); its message schemas are documented in `docs/api.md` and covered by fixtures (D22).

Catch-up is REST-only. After `subscribed`, if `sequence > SyncState.lastSequence` the client calls `GET /v1/projects/{id}/events?after=<lastSequence>&limit=500` until caught up. A live `event` is applied only when `sequence == lastSequence + 1`; otherwise the same REST catch-up runs. The server answers 410 `sequence_too_old` when the gap exceeds 2,000 events, which triggers a snapshot reload (D08). Events are retained forever (D17), so the cap is an efficiency limit, not a correctness window. Duplicate delivery is harmless because application is by sequence.

Publication. The sequence is allocated inside the mutation transaction (D17). The in-process `RealtimeHub` actor (keyed by `projectId` → connections) publishes only after commit through a post-commit hook on the service layer's `Mutation.commit` helper; nothing uncommitted is ever broadcast. There is one `api` process, so no Redis or LISTEN/NOTIFY is needed; the worker never writes project events. Membership removal, role change to self, project archive and project deletion call `hub.evict(userId:projectId:)` after commit, which sends `unsubscribed` and drops the subscription within one second.

Lifecycle. The client sends `ping` every 30 s in the foreground; the server closes after 90 s of silence with 4408; the client reconnects with backoff 1, 2, 4, 8, 16, 30 s plus ±20 % jitter, resets on success, reconnects immediately on `NWPathMonitor` changes (including the Tailscale interface appearing) and on `scenePhase == .active`, re-subscribes to every cached project, and runs REST catch-up. The socket is closed 5 s after entering the background and never opened while in the background. While disconnected in the foreground the client polls `GET events` every 60 s. A "Reconnecting…" capsule appears only after 5 s of disconnection. Close code 1001 from a server restart is treated like a network drop.

Tests (Phase 6): subscribe without membership, duplicate delivery, gap detection, revoke mid-connection, logout closes 4401, archive and delete evictions, reconnect storm backoff, rate-limit close, catch-up equivalence with a snapshot.

### Rationale

Header auth keeps tokens out of URLs and proxy logs; subscription-per-project reuses the exact membership check as REST; a monotonic per-project sequence makes catch-up trivial and testable; one catch-up mechanism keeps the socket protocol to a handful of message types; post-commit publishing guarantees nothing uncommitted is broadcast. Letting sockets outlive access tokens removes in-band re-authentication and hourly reconnects while every revocation path still closes explicitly. A single API process makes an in-memory hub sufficient.

### Rejected alternatives

Token in the query string (logged by proxies); first-frame auth handshake (needed only if headers were unavailable); inline event replay over the socket (duplicates the REST path); Server-Sent Events (no client-to-server subscribe); Redis pub/sub or LISTEN/NOTIFY (multi-process only; revisit if the api is ever scaled or the worker must publish); closing sockets at access-token expiry (hourly reconnects on every device).

### Consequences

The service layer exposes an after-commit hook. The hub tracks sockets by session for revocation. The client needs a small state machine with tests for duplicate delivery and gaps. tailscale serve and Funnel must pass WebSocket upgrades; the ping interval is tunable against their idle timeouts.

### Open risks

Funnel and tailscale serve idle-timeout behavior for long-lived sockets is verified at Phase 10. URLSessionWebSocketTask header support, ping behavior and background suspension semantics on the minimum iOS are verified at Phase 6. The in-process hub is correct only while exactly one api instance runs.

## D14 — Local attachment storage

Expanded in ADR-0004 (`docs/decisions/0004-local-attachment-storage.md`).

### Decision

Storage. Files live on the host at `/Users/kanban/SharedKanban/data/attachments`, bind-mounted at `/data/attachments` (0700, owned by the api user) into `api` and `worker`. Storage key = 32 CSPRNG bytes as 64 lowercase hex characters, sharded as `<k[0..2]>/<k[2..4]>/<k>` with no extension; every key is validated against `^[0-9a-f]{64}$` before any path is built; paths are never derived from user input and Vapor's FileMiddleware is not used.

Metadata. `attachments { id, task_id, project_id (denormalized for authorization), uploader_id, storage_key, original_name (sanitized, control characters and path separators stripped, <= 255 chars), declared_mime, sniffed_mime, byte_size, sha256, state ∈ pending|complete, upload_token_hash, upload_expires_at, session_id, created_at, completed_at, deleted_at }`.

Limits and allowlist. 25 MB per file (413 `payload_too_large`), 20 attachments per task, 2 GB per project, a global cap configurable (default 50 GB), at most 10 pending uploads per user (429 `rate_limited` with `details.reason = "pendingUploads"`), and uploads refused with 507 `insufficient_storage` when the volume has less than 10 % or less than 10 GB free. Quota accounting is `SUM(byte_size)` of complete rows per project. Release-1 allowlist: `image/jpeg`, `image/png`, `image/heic`, `image/heif`, `image/gif`, `image/webp`, `application/pdf`, `text/plain`, `text/markdown`, `video/mp4`, `video/quicktime`. The server sniffs magic bytes (first 512 bytes; `ftyp` brands for HEIC/HEIF/MP4/MOV; `%PDF`; valid UTF-8 without NUL for text) and the sniffed family must match the declared type or the upload fails 415 `unsupported_media_type`. SVG, HTML, zip, OOXML, CSV and executables are excluded (OOXML needs zip inspection and CSV carries formula injection; both are release-2 candidates).

Flow. (1) `POST /v1/tasks/{id}/attachments/initiate { operationId, originalName, declaredMime, byteSize, sha256 }` → 201 `{ attachmentId, uploadPath: "/v1/attachments/{id}/content", uploadToken, uploadExpiresAt (+24 h) }` after role, count, quota, free-space and allowlist checks. The upload token (`skut_` + 32 CSPRNG bytes base64url) is a single-purpose secret hashed at rest, bound to the attachment id, declared size, SHA-256, user and issuing session, because background transfers can finish hours after the access token expired; it is invalidated when the issuing session is logged out or revoked or the account is deleted. (2) The client stages the file (copy from `fileImporter` inside `startAccessingSecurityScopedResource`, or a `FileRepresentation` from `PhotosPicker` to avoid loading 25 MB into memory; location EXIF stripped from photos by default) into `Application Support/uploads/<attachmentId>`, records a `StagedUpload` in the outbox store, and runs `URLSession(configuration: .background("app.sharedkanban.uploads")).uploadTask(with: PUT /v1/attachments/{id}/content, fromFile:)` with `Authorization: Bearer <uploadToken>`; the app delegate adaptor implements `handleEventsForBackgroundURLSession`. (3) The server streams the body to `<k>.part` on the same volume, enforces the declared byte size while streaming, computes SHA-256, sniffs the first bytes, compares the hash with the initiate value, renames atomically to `<k>`, marks `complete`, emits `attachment.added`, and returns 200 with the AttachmentDTO. The PUT is the completion step; the brief's separate `POST /v1/attachments/{id}/complete` is dropped (documented deviation) so there is one fewer state and no worker involvement. The PUT is idempotent by state: a re-PUT on a complete row with a matching SHA-256 returns 200 with the DTO and emits nothing; a mismatch returns 409 `version_conflict`; the PUT carries no operationId and the D18 fingerprint rule does not apply to binary bodies. Progress, Retry and Cancel appear on a row in the task detail; previews use `QLThumbnailGenerator` and `.quickLookPreview`; thumbnails are built on the client only.

Download. `GET /v1/attachments/{id}/content` with the normal access token requires project membership, `state = complete` and `deleted_at IS NULL`; responds with `Content-Type: <sniffed_mime>`, `Content-Disposition: attachment; filename="<ascii-safe>"; filename*=UTF-8''<percent-encoded>`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cache-Control: private, no-store`, and supports `Range`.

Deletion and cleanup. `DELETE /v1/attachments/{id}` (uploader, owner or admin, D03; strict no-op when already deleted) sets `deleted_at` and emits `attachment.deleted`; the worker unlinks the file 24 h later. Hourly, `pending` rows older than 48 h are deleted with their `.part` files; a weekly scan quarantines files that have no row and deletes them after a further 7 days, and flags rows whose file is missing in the owner's System Status screen. Permanent task deletion and project purge delete attachment rows and files through the same worker path.

Tests (Phase 8): traversal attempts in keys and names, sniff-versus-declared mismatch, oversized body, hash mismatch, upload-token reuse, expiry and revocation, unauthorized download, deleted-row download, background resume after suspension, pending-upload cap.

### Rationale

Random keys plus strict validation eliminate path traversal by construction; sniffing plus an allowlist keeps HTML and SVG out of a domain that also serves the AASA and the invite page; a separate 24-hour upload token solves the background-URLSession credential problem without making access tokens long-lived; folding completion into the PUT removes a state, a round trip and the only reason the worker would ever publish an event; quotas and free-space checks keep the single disk from filling silently.

### Rejected alternatives

Storing blobs in PostgreSQL (bloats dumps and backups); presigned object storage or MinIO (a cloud dependency or another service); using the access token on background uploads (expires mid-transfer or must be long-lived); multipart uploads (background sessions need a file body; PUT is simplest); server-generated thumbnails (image parsing attack surface on the server); a separate completion endpoint; a 7-day file grace period (restic snapshots already hold prior versions).

### Consequences

Backups snapshot the directory together with the database dump (D21). The worker needs write access to the volume. Reverse-proxy and tunnel body limits must exceed 25 MB. The background session identifier is stable across launches. The pending-upload cap and free-space floor are surfaced as understandable errors in the UI.

### Open risks

HEIC `ftyp` brand variants from real iPhone photos need a fixture set at Phase 8. Polyglot files are mitigated by the attachment disposition, nosniff and the CSP rather than by sniffing. Very slow uploads over Tailscale from cellular should be observed in the Phase 8 device checklist.

## D15 — MCP adapter semantics, scopes, audit, transport

Expanded in ADR-0005 (`docs/decisions/0005-mcp-proposal-confirmation.md`).

### Decision

Placement. The MCP server is implemented inside the `api` process as a thin layer over the same application services and `ProjectAuthorizer` (D03); it has no queries of its own and no filesystem access. In release 1 it is served as Streamable HTTP at `http://127.0.0.1:8080/mcp` (loopback-only; excluded from every Funnel or tunnel path set until Phase 9b) and accepts only Claude connection tokens (`skct_…`, D16). `Run mcp-stdio` is a stdio bridge launched on the Mac mini by Claude Desktop or Claude Code: it forwards MCP messages to that loopback endpoint with the connection token from its environment and holds no database credentials, no secrets of its own and no filesystem access. Clients that support local HTTP MCP servers may connect to the loopback endpoint directly.

Identity and scopes. A Claude connection token is created in the iOS app (Settings → Connect Claude: shown once, scopes chosen at creation, 90-day expiry, revocable from the same screen) or on the Mac mini with `Run mcp-token create --user <id> --client <name> --scopes …` so a Cowork session can pair Claude Desktop without the owner transcribing anything; it is stored hashed in `mcp_grants { id, user_id, client_id, token_hash, scopes, created_at, expires_at, last_used_at, revoked_at }`. Scopes: `projects:read` and `tasks:read` (default); `tasks:write`, `comments:write`, `projects:write`, `members:read` (explicit grant); `members:manage` (separate explicit opt-in, never default, required by `propose_invite_member` and `propose_remove_member`). Each tool declares exactly one required scope. The token sits in plaintext in the Claude client's configuration on the Mac mini, readable by that macOS user; this is accepted for the trusted host and stated in the threat model.

Tools. Read tools (`list_projects`, `get_project`, `list_tasks`, `get_task`, `search_tasks`, `list_project_members`) execute immediately under the bound user's permissions; `search_tasks` matches title, notes and comment bodies case-insensitively and excludes archived tasks unless `includeArchived` is true. Every mutation tool (`propose_create_task`, `propose_update_task`, `propose_move_task`, `propose_comment`, `propose_create_project`, `propose_invite_member`, `propose_remove_member`) only writes `PendingAIChange { id, user_id, client_id, project_id, tool, operations (typed JSON list, each with its own pre-generated operationId), diff [{entity, field, old, new}], captured_versions {entityId: version}, risk_level, required_scope, confirmation_token_hash, state ∈ pending|confirmed|cancelled|expired|failed, created_at, expires_at (+10 minutes), confirmed_at, result_sequence }` and returns the diff, affected project and cards, risk level, required scope, expiry and a one-time `confirmation_token` (32 CSPRNG bytes base64url, hashed at rest). Nothing auto-applies in release 1; an auto-apply preference is deliberately not built. Risk levels (display and audit only, since everything requires confirmation): low = one task created, updated, moved or commented; medium = project creation, assignee change, due-date removal; high = any proposal touching more than one task, invitations, removals, archive. Tools carry MCP annotations (`readOnlyHint`, `destructiveHint`) so clients can prompt appropriately.

Confirmation. `confirm_change(change_id, confirmation_token)` atomically transitions `pending → confirmed` (single use), checks the token hash, user, `client_id` and expiry, re-runs full authorization at confirmation time (membership or role lost between proposal and confirmation → `failed`, 403), verifies that every captured entity version is unchanged (otherwise 409 `stale_proposal` and the model must re-propose, so the diff shown is exactly what gets applied), then executes the operations in order through the normal services with the stored operationIds (D18, so a double confirm cannot double-apply) and `via = mcp`, and returns the committed sequence. A second confirmation of the same change → 409 `change_already_applied`. `cancel_change` marks cancelled. Pending proposals are not project events; only confirmed changes produce normal activity events, shown in the feed as "<Name> via Claude".

Validation and limits. Strict JSON Schemas with `additionalProperties: false`, string caps (title 200, notes 20,000, comment 5,000), array caps (50), every id validated against the user's projects (cross-project ids → not found), undeclared parameters rejected. Rate limits: 60 read calls and 10 proposals per minute per grant. Content returned by read tools (notes, comments) is untrusted input to the model: control characters are stripped and the audit log records every call, but prompt injection through task content cannot be prevented by the server, which is one more reason nothing auto-applies.

Audit. `mcp_audit_log { id, at, user_id, client_id, tool, args_redacted (truncated to 4 KB), project_id, change_id, outcome ∈ ok|denied|error, error_code, duration_ms, remote_addr }` written for every call including denials, retained 1 year, included in backups, readable by the user in Settings → Claude activity (`GET /v1/mcp/audit`).

Human veto. In release 1 the human opportunity to deny rests on the MCP client's per-call approval, because the model receives the confirmation token in the proposal response and can call `confirm_change` itself. This dependency is documented in the connector setup instructions. An in-app approval mode (a push "Claude proposes …" with Approve in the iOS app before `confirm_change` succeeds) is a release-2 candidate.

Production transport (Phase 9b, built only if the owner wants claude.ai or phone access). Streamable HTTP at `https://<host>/mcp` on the public profile (D10) implementing the MCP authorization specification current at that time: protected-resource metadata at `/.well-known/oauth-protected-resource`, a minimal Vapor authorization server (authorization code + PKCE, resource indicators so tokens are audience-bound to `/mcp`, 1-hour access tokens, 30-day rotating refresh tokens, per-grant scopes, dynamic client registration if the connector requires it), and a consent step completed in the iOS app: the authorization page shows an 8-character pairing code, the user approves it in Settings → Connect Claude, which lists the requested scopes; no web Sign in with Apple is needed.

Tests (Phase 9): cross-project ids, injected arguments, overlong strings, duplicate and expired confirmation, membership removal between proposal and confirmation, stale captured versions, undeclared parameters, denied scope, token for another audience (9b).

### Rationale

Proposal and confirm with a user-bound single-use token gives a human veto on every write, exactly as the brief and the MCP guidance ask; capturing versions makes confirmation safe against concurrent human edits; re-authorizing at confirm time closes the propose-then-removed gap. Keeping the MCP server in the api process and making the stdio bridge a credential-free client keeps one authorization path and no credentials in the AI-launched process. Always-confirm is the simplest safe policy, and deferring OAuth to a need-driven phase removes the largest non-product component from release 1.

### Rejected alternatives

Auto-applying low-risk changes in release 1 (removes the veto before the audit trail is proven); an in-process adapter launched by Claude Desktop (would hold database credentials); static API keys in config for production (cannot be scoped or rotated per client; forbidden by the brief); web Sign in with Apple on the consent page (Services ID, domain verification and more human steps); a 6-digit pairing code (brute-forceable without stricter limits).

### Consequences

Phase 9 scope is the stdio bridge, the proposal engine, scopes, the audit log and the in-app Connect Claude screen. Phase 9b adds a small OAuth server only when needed. PendingAIChange executes through the same idempotency path as the app. `/mcp` must be rate-limited like auth endpoints once it is public.

### Open risks

The MCP authorization specification and Claude connector support for custom OAuth servers are moving targets; the version current at Phase 9b must be recorded. Claude Desktop's support for local HTTP servers versus stdio must be checked against the client the owner actually uses.

## D16 — Session and token lifecycle

### Decision

Token classes. Opaque tokens only, no JWTs for the app. Session access token `skat_<sessionId>.<32 CSPRNG bytes base64url>`, lifetime 60 minutes; refresh token `skrt_<32 bytes base64url>`, 90-day sliding lifetime with an absolute maximum of 365 days from session creation; upload token `skut_…` (D14); Claude connection token `skct_…` (D15, accepted only by `/mcp`). Raw tokens are never logged or stored; only SHA-256 hashes are kept.

Session row, one per app installation: `sessions { id, user_id, installation_id (UUID minted at first launch, stored in Keychain, not synced), access_token_hash, access_expires_at, refresh_token_hash, refresh_expires_at, absolute_expires_at, previous_refresh_token_hash, previous_valid_until, rotated_at, device_name, device_model, os_version, app_version, last_ip_prefix (/24 or /48), created_at, last_used_at, revoked_at, revoke_reason }`. Device rows (D07) reference `session_id`.

Verification per request and per WebSocket upgrade: parse the session id from the access token, load the row, constant-time compare the hash, check `access_expires_at`, `revoked_at IS NULL`, and `users.deleted_at IS NULL` (one indexed query plus the user).

Issuance and rotation. `POST /v1/auth/apple` creates the session and returns the first pair. `POST /v1/auth/refresh {refreshToken}` atomically issues a new access and refresh pair, moves the old refresh hash to `previous_refresh_token_hash` with `previous_valid_until = now + 60 s`, and extends the sliding window. A refresh token matching `previous_refresh_token_hash` within the grace window (a retry after a lost response) issues another fresh pair that supersedes the lost one; any other non-current token, or the previous token after the window, revokes the whole session (`revoke_reason = refresh_reuse`), returns 401 `session_revoked`, writes a `security.session_reuse` audit row, and pushes "Signed out for your safety" to the user's other devices. The client serializes refreshes (single flight), refreshes proactively when fewer than 5 minutes remain, retries once on 401 `token_expired`, and otherwise shows the sign-in screen while keeping the outbox (D08).

Endpoints. `POST /v1/auth/logout` revokes the current session, deletes its device row and invalidates its upload tokens; `GET /v1/auth/sessions` lists own sessions (device name, model, last used, current flag); `DELETE /v1/auth/sessions/{id}`; `POST /v1/auth/sessions/revoke-all {keepCurrent: Bool}`. Every revocation closes that session's WebSockets (D13) and invalidates upload tokens issued under it. Housekeeping: expired and revoked rows older than 30 days purged daily; sessions whose refresh window lapsed are expired.

Keychain. Items use `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, are non-synchronizable, and are stored as one `Codable` blob; a first-launch flag detects Keychain items left over from an uninstall and wipes them. The Apple identity token is never stored; Apple's refresh token is stored encrypted only for revocation (D09). App Attest is explicitly not used in release 1 (documented deviation from the brief's "app attestation context"; revisit if abuse ever appears). Rate limits: `/v1/auth/apple` 10 per minute per IP and 5 per minute per user; `/v1/auth/refresh` 30 per minute per session; failed Apple verifications are logged with reason codes only.

### Rationale

Opaque hashed tokens give instant revocation and no signature or algorithm footguns; one indexed lookup per request is trivial at household scale and the per-request membership check needs the database anyway. Rotation with reuse detection is the standard defense against stolen refresh tokens, and the 60-second grace window stops a legitimate retry after a dropped response from signing the user out. A 90-day sliding window suits a household where an iPad can sit unused for a month. Per-installation sessions make "sign out that old iPad" meaningful and let device records and upload tokens follow the session.

### Rejected alternatives

JWT access tokens (revocation lag, key management, algorithm confusion); non-rotating or long-lived single bearer tokens; 15-minute access tokens (force in-band WebSocket re-auth for no household benefit); refresh token families with full history tables (more rows for the same detection); iCloud Keychain sync (sessions are per installation by design); App Attest in release 1.

### Consequences

The hub must subscribe to session revocation. Settings gains a sessions list in Phase 3. The incident runbook item "stolen refresh token" is satisfied by revoke-all plus reuse detection. NTP must be on at the Mac mini (D21) because all expiry comparisons are server-side.

### Open risks

A device with a wildly wrong clock sees only Apple identity-token failures (handled by Apple JWT verification tolerance); server-side token expiry is unaffected. A refresh race that straddles the 60-second window is still a lockout, which is acceptable because the client single-flights refreshes.

## D17 — Activity event log and project sequence

### Decision

Table. `activity_events { id uuid PK, project_id, sequence bigint, actor_user_id nullable (null for system), via ∈ app|mcp|system, action text, entity_type ∈ project|column|task|comment|attachment|member|invitation, entity_id uuid, entity_version int nullable (the entity's version after this change; null for events that do not bump a version, such as column.ranks_normalized), changes jsonb, extra jsonb, operation_id uuid nullable, created_at timestamptz }` with unique `(project_id, sequence)` and an index on `(entity_type, entity_id, entity_version)` for D05 merges. For `via = mcp`, `actor_user_id` is the confirming user.

Action vocabulary, a closed enum in SharedDTOs that clients decode to `.unknown` while still advancing the sequence: `project.created|renamed|archived|unarchived|deleted|restored|ownership_transferred`; `column.created|updated|reordered|archived|restored|ranks_normalized`; `task.created|updated|moved|archived|restored|deleted`; `comment.added|edited|deleted`; `attachment.added|deleted`; `member.joined|left|removed|role_changed`; `invitation.created|revoked|declined`. Acceptance is recorded as `member.joined` with `extra {invitationId, inviterUserId}`.

Metadata. `changes = { field: { from, to } }` keyed by DTO field names (the same identifiers as PATCH bodies, D05), with string values truncated to 200 characters and `truncated: true`; `extra` holds action-specific data: `task.moved` carries `{fromColumnId, toColumnId, wipExceeded, completionChange}`, `column.ranks_normalized` carries `{ranks: [{taskId, rank}]}`, `column.reordered` carries `{orderedColumnIds}`, membership events carry `{userId, role, fromRole}`, comment events carry `{commentId, preview}`. Never stored: emails, tokens, attachment names beyond 100 characters, full notes. Not recorded at all: reads, sign-ins, token refreshes (structured server logs only).

Sequence allocation. Every project-scoped mutation runs inside one transaction that first takes `SELECT ... FOR UPDATE` on the project row (D06), performs the domain writes, then executes `UPDATE projects SET last_sequence = last_sequence + 1 WHERE id = $1 RETURNING last_sequence` once per event; because the lock is held until commit, sequence order equals commit order per project, and rollbacks leave no gaps. A single `Mutation.commit` helper writes the entity change, the event(s), and the idempotency record (D18) and registers the post-commit publication (D13); a mutation without an event is a bug caught by tests. Invariant: every increment of an entity's version is recorded by exactly one event carrying that `entity_version`; a mutation request normally writes one event (a PATCH changing three fields is one `task.updated` with three `changes` keys), and a move that renormalizes writes two (`task.moved`, then `column.ranks_normalized`).

Retention. Forever. Deleted projects take their events with them at purge. The 2,000-event catch-up cap (D13) is an efficiency limit only. Metadata fragments (notes and comment previews) persist after a comment is deleted or an author is anonymized; this is disclosed in the privacy inventory. Display names are never stored in events; the client resolves `actor_user_id` against its member cache at render time so renames and "Deleted member" are reflected.

Consumers. The same rows serve the realtime stream (D13), REST catch-up, the member-facing activity feed (`GET /v1/projects/{id}/activity?before=<sequence>&limit=50`, rendered on the client with per-action sentences and visual coalescing of consecutive events by the same actor within one minute), the notification outbox (D07), and conflict detection (D05). Worker consumers keep per-project cursors in `worker_cursors { job, project_id, last_sequence }` and discover work by comparing `projects.last_sequence` with the cursor, which is exact because sequences are gap-free and commit-ordered.

### Rationale

One table serving four consumers means getting it right once pays everywhere. Allocating the sequence under the project row lock is the simplest correct monotonic counter and doubles as the serialization point the brief wants for moves. Retaining events forever removes the compaction job and the fragile coupling of retention to queue age and idempotency TTL; at household volume the table stays tiny. Per-project cursors avoid the non-monotonic-id trap of a global cursor.

### Rejected alternatives

A global sequence (clients would filter, unrelated projects couple); PostgreSQL sequences (not transactional, gaps break "next must be last + 1"); a UUID- or serial-based worker cursor (not commit-ordered, can skip events); storing full before/after bodies (privacy and size); event pruning (breaks nothing today but buys nothing either); event sourcing as the source of truth (tables remain authoritative); separate feed, sync and notification tables (drift).

### Consequences

Every service mutation goes through `Mutation.commit`. Write throughput is serialized per project, which is fine for a household and is documented; long attachment or MCP operations must not hold the lock (uploads touch the project lock only in the final metadata write). The client needs human-readable rendering per action.

### Open risks

Truncated change values mean the feed cannot show full old notes (acceptable). Bulk effects such as assignee clearing on member removal create one event per task; the feed coalesces visually.

## D18 — Idempotency

### Decision

Carrier. Every mutating JSON request with `POST` or `PATCH` carries `operationId` (UUID v4) in the body as part of the typed DTO (the brief's field name). `DELETE` requests carry no body and no operationId: every DELETE is defined as a strict state no-op when the target is already in the requested state (archiving an archived task, revoking a revoked invitation, deleting a deleted attachment, removing a non-member) and returns the same status with no new event. `PUT` requests (attachment content, device registration, notification settings) are full replacements and idempotent by state. Auth endpoints carry no operationId. The brief's `DELETE /v1/account` therefore becomes `POST /v1/account/delete` (D09). The `Idempotency-Key` header is not used.

Table. `operations { user_id, operation_id, request_hash (SHA-256 of method + path + canonical JSON body with sorted keys, explicit nulls preserved, no floats in any DTO), status_code, response_body jsonb, created_at, completed_at }` with primary key `(user_id, operation_id)`; scope is per user, so the same UUID from another user is a different operation.

Flow, inside the mutation transaction. `INSERT ... ON CONFLICT DO NOTHING RETURNING` the operation row first: a concurrent duplicate blocks on the primary key until the first transaction finishes, so no visible in-progress state is needed. If the row was inserted, the mutation runs inside a `SAVEPOINT`: on success the row is updated to `completed` with the status and body and the transaction commits; on a storable failure (409 or 422 except `idempotency_mismatch`) the savepoint is rolled back, the failure status and body are stored, and the transaction commits; on any other failure (401, 403, 404, 429, 5xx, transport) everything rolls back and the retry is a fresh evaluation. If the row already existed: the same `request_hash` replays the stored status and body verbatim with the header `Idempotency-Replayed: true`, re-emitting no events and no pushes; a different hash returns 422 `idempotency_mismatch`. A replayed 409 stays a 409: after the user resolves a conflict the client always mints a new operationId with the corrected input. The replayed body may contain a `sequence` that is now stale (harmless, documented so tests do not assert otherwise). Events written by the operation carry `operation_id` so clients recognise their own echoes during catch-up.

TTL. 30 days, purged daily, matching the offline queue age-out (D08): the outbox never replays an operation older than the TTL. MCP confirmations use the per-operation ids generated at proposal time (D15), so a double confirm cannot double-apply.

Tests (Phase 2): replay returns the identical body and header, mismatch, concurrent duplicates, stored 409 replay, non-stored 5xx retry, DELETE no-op without a second event, TTL purge.

### Rationale

A body field keeps the key inside the typed DTO shared by app and MCP and visible in tests; the DELETE no-op rule removes the need for a second mechanism; inserting the record inside the mutation transaction gives exactly-once semantics without an in-progress state machine or abandoned-row sweeper; storing conflicts makes a retry after a lost response deterministic ("a retry can only ever see the outcome it missed"); the per-user scope prevents cross-user replay; 30 days covers the longest offline period the product promises.

### Rejected alternatives

`Idempotency-Key` header (two mechanisms once bodies exist; invisible to DTO tests); header plus body with a mismatch rule (the worst of both); per-project scope (project creation has no project yet); storing only successes (a retry could silently succeed against a state the user never saw); an in-progress state with a 5-minute sweeper (unnecessary once the insert is transactional); in-memory keys (lost on restart, exactly when retries happen).

### Consequences

Request canonicalization must be deterministic (sorted keys, nulls kept) in Vapor middleware and must mirror the `Patch<T>` encoding. Clients never reuse an operationId after changing the payload. The savepoint pattern must be expressible through Fluent plus raw SQLKit (verify at Phase 2). Every archive or revoke operation must be implemented as a strict no-op on repeat.

### Open risks

A stored response replayed later may contain data the user has since lost access to; user scope keeps the risk low and a membership re-check runs on replay anyway. Stored response sizes stay small because mutations return single entities; table size is monitored.

## D19 — Workflow invariants, templates, WIP, archive, completion

### Decision

Columns. `columns { id, project_id, title (1–40 chars), rank (D06), color (named semantic token, not hex), wip_limit (null or 1–99), is_done, version, archived_at, timestamps }`. Active means `archived_at IS NULL`. Columns are archived, never deleted, so archived tasks always point at an existing column.

Invariant. 3 ≤ active columns ≤ 4 per project, enforced twice: (a) in the service layer under the project row lock — creating a column that would make 5 → 422 `column_count_invalid`; archiving one that would leave 2 → 422 `column_count_invalid`; archiving a column that still holds active tasks requires `moveTasksTo=<columnId>` on `DELETE /v1/columns/{id}` (otherwise 422 `column_not_empty`), and the moved tasks are appended to the target column's bottom with `task.moved` events; `POST /v1/columns/{id}/restore {operationId}` fails 422 `column_count_invalid` at 4; (b) a PostgreSQL deferrable constraint trigger that counts active columns per project at commit and raises outside 3–4, catching bugs and manual SQL. Project creation is atomic with its template columns.

Templates. Defined once in SharedDTOs (`ProjectTemplate`) and used by the server for creation and by the client for previews and the Phase 4 prototype: `homeProjects` → Backlog, To Do, In Progress, Complete; `restaurantsToTry` → Backlog, Scheduled, Complete; `custom(titles:)` → 3 or 4 user-entered names. In every template the last column is the done column by default. Stable ids `home-projects`, `restaurants-to-try`, `custom`.

Completion. At most one column per project has `is_done = true` (partial unique index). Moving a task into it sets `completedAt = now()` (server clock) and moving out clears it; `task.moved` carries `completionChange` for the feed and notifications. Reassigning the flag (owner/admin, `PATCH /v1/columns/{id} {isDone: true}`) clears the old flag in a first statement and sets the new one in a second statement within the transaction, never retroactively changes existing `completedAt` values, and may be cleared entirely; archiving the done column clears the flag and the UI shows "No column marks tasks complete" until one is chosen. There is no per-task checkbox. Completed tasks stay on the board with a checkmark, remain searchable, are excluded from reminders and overdue styling, and count toward their column's WIP like any active task. `POST /v1/projects/{id}/tasks/archive-completed {operationId}` (editor and above) is the only bulk action in release 1; no automatic archiving runs.

WIP. Optional 1–99 per column; the header shows `count/limit`, amber at the limit and red above, with the `exclamationmark.triangle` symbol and a VoiceOver suffix "over the limit of N"; drops and moves are never blocked, the server never rejects on WIP, and `task.moved` records `wipExceeded`. The brief's "pull habit" is encouraged only by this indicator; no further nudges are a release-1 goal.

Task archive and delete. `DELETE /v1/tasks/{id}` archives (sets `archived_at`, removes from the board, keeps the task in search under an Archived filter and in Project → Archived tasks; editor and above; strict no-op when already archived). `POST /v1/tasks/{id}/restore {operationId}` returns the task to the bottom of its column, or of the first column if its column is archived. `DELETE /v1/tasks/{id}?permanent=true` is owner/admin only, allowed only for already-archived tasks, requires a confirmation alert, writes `task.deleted`, and removes comments and attachment rows with files deleted through the worker path (D14). No automatic purge of archived tasks in release 1. New tasks enter the first column unless created from a specific column's Add button.

UI. The New Project sheet shows the two templates and Custom as cards with a tiny column preview, then an editable list of names. Add Column is disabled at 4 with the footnote "Projects have three or four columns in this version"; Archive Column is disabled at 3 or when the column holds tasks, with "Move all tasks to…" offered first. On iPhone, column reorder lives in Project settings → Columns with drag handles plus Move Up / Move Down menu items; on iPad the same list is also reachable from the column overflow menu. Search supports `includeArchived`.

### Rationale

Enforcing the count at both service and database levels keeps the invariant true through restores, migrations and future tooling. Archiving instead of deleting columns avoids dangling references from archived tasks. A single `is_done` flag gives completion semantics without a second source of truth and makes "completed" unambiguous for Claude's search tools. Warn-not-block WIP matches the brief's household stance. Archive-first keeps deletion a deliberate, role-gated second step.

### Rejected alternatives

Allowing 2 or 5+ columns with a soft warning (the brief says exactly 3 or 4); deleting columns (dangling references or forced task moves on delete); inferring done from the column name (breaks on rename); a separate `isCompleted` task flag (two sources of truth); hard-blocking WIP; a worker-driven auto-archive of completed tasks (adds a job and a worker publication path for a feature nobody asked for); hard delete as the default.

### Consequences

Migrations create the constraint trigger and the partial unique index. The move service reads the `is_done` flag. Column reorder takes the full ordered id list with `expectedProjectVersion` (D06). The prototype's sample data mirrors the templates from SharedDTOs.

### Open risks

Users who want a fifth stage hit the wall; relaxing the cap is a release-2 candidate with the trigger parameter as the only change. A done column that is not last is allowed; the iPhone switcher order follows rank, so clarity is tested at Phase 4.

## D21 — Backup and restore

### Decision

Tool and schedule. restic (encryption, deduplication, retention, verification, multiple targets) driven by `deploy/backup/backup.sh` from a host launchd job (not a container, so it reaches the USB SSD and iCloud Drive natively and does not depend on the worker). Every 6 hours: `docker compose exec -T postgres pg_dump -Fc` to `/Users/kanban/SharedKanban/data/backups/db/<timestamp>.dump` (last 8 kept locally), then `restic backup` of the dumps directory and the attachments directory into the primary repository on the external USB SSD (`/Volumes/KanbanBackup/restic`); RPO to the SSD is 6 hours. Nightly at 02:30: `restic copy` from the primary repository to the secondary, off-device repository, whose default is an iCloud Drive folder (`~/Library/Mobile Documents/com~apple~CloudDocs/SharedKanbanBackup`, "Optimize Mac Storage" off; the repository is ciphertext so iCloud never sees data) with Backblaze B2 or any S3-compatible bucket as the documented alternative if iCloud proves unreliable; RPO off-device is 24 hours. Retention on both: `restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune` weekly; `restic check --read-data-subset=10%` weekly on both repositories. The dump and the attachment snapshot are not point-in-time consistent with each other; `.part` files are excluded and the drill tolerates files without rows.

Secrets. The restic password lives in `/Users/kanban/SharedKanban/secrets/restic-password` (0600) and in the owner's password manager. The secrets directory (`.env`, both .p8 keys, the restic password) is never inside a restic repository; `deploy/backup/export-secrets.sh` writes an encrypted disk image of it to the SSD after any change, with a passphrase the owner keeps in the password manager. No second encryption layer (such as age) is added on top of restic.

Restore. `deploy/backup/restore.sh <snapshot>` restores into a disposable Compose project `sharedkanban-drill` on alternate ports with blank Apple and APNs credentials (so a drill can never push real notifications or revoke real tokens), runs migrations status, verifies row counts, re-hashes every complete attachment against `attachments.sha256`, and starts the API for `/ready`, a fake-login and a project-read smoke test. A monthly automated drill is scheduled by launchd and its result is shown in the owner's System Status screen; a quarterly human-observed drill is run by Cowork from the checklist in `deploy/runbook.md` and the owner reads a one-paragraph result. A real recovery stops the live stack first.

Monitoring without external accounts. The worker records last-backup time, last check result, last drill result and disk free, exposes them on `/ready` and in Settings → Server status, and pushes an alert to the owner's devices when the last successful backup is older than 30 hours, a check or drill fails, the SSD is missing, or free space is below 20 % (uploads stop at 10 % or 10 GB, D14). Because the worker cannot alert when Docker itself is down, two out-of-band checks exist: a host launchd `health.sh` that probes `/ready` every 5 minutes, writes `~/SharedKanban/status.json`, and restarts Docker Desktop and the Compose stack after three consecutive failures; and a client-side watchdog in the app (`BGAppRefreshTask`, best effort) that posts a local notification "SharedKanban server unreachable since <time>" after 24 hours without a successful sync while the device was online.

Host stance. UPS over USB with macOS set to shut down after 5 minutes on battery and to start up automatically after a power failure (`pmset autorestart 1`); the service user `kanban` auto-logs in so Docker Desktop and Tailscale start unattended. FileVault is OFF by default on the Mac mini because macOS disables automatic login while FileVault is on and an unattended restart would otherwise stall until someone types a password; the owner may choose FileVault ON and accept manual unlock after any full restart (the runbook documents both). Theft of the Mac mini is treated in the incident runbook as a full compromise (revoke all sessions, rotate the APNs and Sign in with Apple keys). NTP on; automatic security updates on with restarts scheduled after a backup; automatic major upgrades off; Time Machine is not used for app data (restic is authoritative); the external SSD is excluded from Spotlight and Time Machine.

### Rationale

restic gives encryption, dedup, integrity checks and multi-target in one well-maintained tool, so the dumps and the attachment directory share one restore story; six-hourly dumps bound data loss to a few hours of household edits; a `restic copy` means one verified backup and one verified copy rather than two independent runs; iCloud Drive avoids a new account and card; a scripted drill into a throwaway stack is the only proof a backup works; pushing status to the owner's phone avoids yet another cloud account. The host launchd placement and the client watchdog remove the "Docker is down so nothing alerts" blind spot.

### Rejected alternatives

Plain `pg_dump` + `tar` + cron with hand-rolled encryption (more scripts, no integrity checks, no dedup); WAL archiving and PITR (more than a two-user app justifies); Time Machine only (not application-consistent); a backup container (cannot reach the SSD and iCloud Drive without file-sharing configuration and dies with Docker); a Backblaze account as the first off-device target (one more human account); double encryption with age (a second key to lose, breaks automated drills).

### Consequences

restic is a Homebrew dependency on the host. Phase 10 produces `backup.sh`, `restore.sh`, `health.sh`, `export-secrets.sh`, the launchd plists, the drill and the status screen. The owner's physical steps are the SSD and the UPS. The FileVault default is recorded as an owner decision in the runbook.

### Open risks

iCloud Drive syncing of a restic repository (many small pack files) is unproven; it is verified with a week of runs at Phase 10 before being trusted, with B2 as the fallback. FileVault OFF trades disk encryption for unattended availability; the owner must confirm. A lost restic password equals lost backups.

## D22 — API conventions

### Decision

Versioning and format. All routes under `/v1`; a breaking change creates `/v2` while `/v1` stays for at least 90 days after the app that uses it is replaced; additive changes (new optional fields, new enum cases) stay in `/v1`. Clients ignore unknown fields and decode unknown enum cases as `.unknown` through a shared `LenientEnum` decoding helper applied to every enum in SharedDTOs. JSON only, `Content-Type: application/json; charset=utf-8`, camelCase keys, 1 MB body limit except attachment content. SharedDTOs exports `JSONCoding.encoder` and `JSONCoding.decoder` used by server and client: timestamps are ISO-8601 UTC with milliseconds and `Z` (`2026-10-01T12:34:56.789Z`), decoded leniently with or without fractional seconds; UUIDs are version 4, documented lowercase, compared case-insensitively because Foundation encodes them uppercase; clients may supply `id` on create for tasks, columns, comments and projects (a collision → 409 `duplicate_id`). The WebSocket message schemas (D13) are documented and fixture-tested alongside REST.

Success shapes. A single resource is returned as the top-level DTO; lists are `{ "items": [...], "nextCursor": "<opaque base64url>" | null }` with `?cursor=&limit=` (default 50, max 200); events use `?after=<sequence>&limit=` (max 500) and the feed `?before=<sequence>`. Single-resource mutations return the DTO with the optional response headers `X-Project-Sequence` (the sequence of the event written) and `X-Merged-From-Version` (D05); the move endpoint returns the object defined in D06.

PATCH semantics. Absent field = unchanged, explicit `null` = clear, implemented by the `Patch<T>` wrapper in SharedDTOs whose custom `Codable` is tested for all three states; `operationId` (D18) and `expectedVersion` (D05) are body fields.

Error envelope, always: `{ "error": { "code": "<snake_case>", "message": "<human sentence safe to display>", "details": { ... } | null, "requestId": "<uuid>" } }`. Codes and statuses: `invalid_request` 400; `unauthenticated`, `token_expired`, `session_revoked`, `reauth_required` 401; `forbidden` 403 (role insufficient inside a project the caller belongs to); `not_found` 404 (also any id outside the caller's projects, so existence never leaks; the log records the real reason with the requestId); `version_conflict`, `position_conflict`, `neighbors_changed`, `task_archived`, `project_archived`, `owner_must_transfer`, `owned_projects_require_transfer`, `change_already_applied`, `stale_proposal`, `duplicate_id` 409; `invitation_unavailable` (details.reason), `sequence_too_old` 410; `payload_too_large` 413; `unsupported_media_type` 415; `validation_failed` (details.fields: [{path, reason}]), `column_count_invalid`, `column_not_empty`, `idempotency_mismatch` 422; `upgrade_required` 426; `rate_limited` 429 with `Retry-After`; `internal` 500 (generic message, requestId points to logs); `insufficient_storage` 507. The code list is one Swift enum in SharedDTOs shared by both sides.

Headers. `Authorization: Bearer <token>`; `X-Request-Id` (generated when absent, validated as at most 64 characters of `[A-Za-z0-9-]` or replaced, echoed, logged, and included in error bodies); `X-Client-Version` (the server enforces a configurable minimum with 426 `upgrade_required`); `Idempotency-Replayed: true` on replays. Security headers on every response: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store` on all JSON.

Rate limits. `/v1/auth/*` 10 per minute per IP and 5 per minute per user; `/v1/auth/refresh` 30 per minute per session; invitation preview/accept/decline 10 per minute per user and 30 per IP; invitation creation 5 per project per hour; attachment initiate 30 per hour per user; MCP 60 reads and 10 proposals per minute per grant; WebSocket 10 inbound messages per second; everything else 600 per minute per user. IP limits apply only where the client address reaches the origin (D10).

Examples policy. `docs/api.md` contains, for every endpoint and every WebSocket message, one request example, one success example and one error example per distinct code; every example is a JSON fixture under `shared/Fixtures/` decoded by SharedDTOs contract tests on Linux and iOS, so documentation cannot drift from the types. The brief's outline deviations are listed in one table: invitation token in the body, `/complete` folded into the attachment PUT, `DELETE /v1/account` as `POST /v1/account/delete`, `DELETE /v1/columns/{id}` archives rather than deletes.

### Rationale

A fixed error shape with stable codes lets the app map errors to understandable UI states and lets tests assert on codes instead of strings; `not_found` for non-member projects is the standard anti-enumeration choice; cursor pagination and sequence-based event paging avoid offset drift; one shared coder removes the two Swift pitfalls (uppercase UUIDs, fractional seconds) that otherwise bite on day one; fixtures-as-tests make "docs match implementation" mechanically checkable, which is the CLAUDE.md definition of done.

### Rejected alternatives

A `{data, meta}` envelope on every response (noise for a typed client); offset pagination (drifts under concurrent edits); RFC 7807 problem+json (fine, but the flatter envelope maps better to Swift errors and there are no external consumers); numeric error codes; header-based idempotency (D18); versioning via headers.

### Consequences

SharedDTOs owns `APIError`, `Page<T>`, `Patch<T>`, the error-code enum, the action enum, the coder configuration and every request, response and event type. Vapor error middleware converts every thrown error to the envelope and never leaks stack traces. Every new endpoint needs a fixture and a doc entry. MCP tool results reuse the same DTOs.

### Open risks

Foundation's ISO-8601 fractional-seconds behavior differs across platforms; the shared formatter is tested on Linux and iOS. Returning 404 for forbidden projects can confuse debugging; logs carry the real reason.

## Unresolved risks

- Availability versus disk encryption on the Mac mini: FileVault OFF (the default here) is what allows unattended restarts and Docker Desktop auto-start; FileVault ON means any full restart stalls until someone types the password. The owner must choose; the runbook documents both.
- Tailscale as the release-1 production transport requires the VPN to be on for both phones, depends on `tailscale serve`/`cert`/`funnel` support in the macOS variant installed, on key-expiry being disabled for the Mac mini, and, if public access is ever enabled, on Funnel's WebSocket, idle-timeout and bandwidth behavior; all verified at Phase 10, with Cloudflare Tunnel as the fallback that changes the privacy posture (edge decryption) and adds a domain and account.
- Universal links need a publicly reachable AASA; in the Tailscale-only profile invitations rely on the content-free `/invite` page, the custom scheme and the code field unless the Associated Domains developer-mode experiment at Phase 7 succeeds.
- Apple Developer Program enrollment, 2FA, the Sign in with Apple and APNs keys, Associated Domains and device trust are unavoidable human steps that can take days and gate Phases 3 and 8; they must be started during Phase 1.
- iPhone drag-and-drop specifics (drop targets inside a paging ScrollView, context-menu and draggable coexistence, edge-dwell paging during a live drag, no vertical auto-scroll) are unverified until Phase 6 on a real device; pills and the Move To menu are the guaranteed fallback.
- Field-level merge relies on every mutation writing complete `changes` keys; the one-event-per-version test is the only guard, and any path that forgets degrades to always-409 for that field.
- The single-process in-memory WebSocket hub is correct only while exactly one api instance runs; any scale-out or any worker-published event requires a pub/sub layer (LISTEN/NOTIFY) that is deliberately not built now.
- The human veto on MCP mutations rests on the MCP client's per-call approval in release 1 because the model holds the confirmation token; prompt injection through task content cannot be prevented server-side. The in-app approval mode is deferred.
- The MCP authorization specification and Claude connector support for custom OAuth servers are moving targets; remote access (Phase 9b) is designed against whatever is current then and may not be needed at all.
- Docker Desktop on a headless, auto-login Mac mini is an operational soft spot (GUI session, VM memory, bind-mount file sharing, behavior after macOS updates); the launchd path is the escape hatch and must be exercised in Phase 10, not merely documented.
- iCloud Drive as the off-device restic target is unproven for many small pack files; a week of monitored runs at Phase 10 decides, with Backblaze B2 as the fallback that adds one human account step.
- The offline draft overlay and overlay-aware fetch are the most intricate client code; "server event arrives for an entity with a pending draft" is the scenario most likely to hide bugs.
- Local-only due reminders can be stale on a device that has not synced; accepted for release 1 and measured in beta.
- Retaining comments, attachments, tasks and event metadata fragments after account deletion under "Deleted member" must be disclosed in the App Store privacy inventory and may need adjusting if a reviewer objects.
- The Mac mini remains a single point of failure (power, disk, home internet); the UPS and external SSD are human purchases, and data durability is unproven until the first restore drill passes.
- All exact platform and library versions as of 2026-10-01 are unverified (see the assumptions below).

## Assumptions to verify at Phase 1

- Both household devices run iOS/iPadOS 18 or later; iOS 18.0 is at least two majors behind the current release on 2026-10-01, so it is a conservative minimum; if both devices run the current major, the minimum is raised to the previous major at Phase 4.
- The latest shipping Xcode at Phase 1 supports an iOS 18.0 deployment target, Swift 6 language mode with strict concurrency and the current SDK; the exact version is recorded then, and no betas are used.
- The latest stable Swift 6.x toolchain is available for both Linux (`swift:6.x` images) and the Mac mini at the same version.
- Vapor 4.x remains the stable line and builds cleanly under Swift 6 strict concurrency; if Vapor 5 has a stable release it is evaluated once and recorded in an ADR; if the chosen Vapor is not clean under Swift 6 mode the server pins Swift 5 mode. Fluent 4, `fluent-postgres-driver` on PostgresNIO, JWTKit 5, APNSwift and swift-crypto are current and maintained.
- PostgreSQL 17 is an appropriate major to pin for the life of release 1; if a newer major is the better long-term pin at Phase 1 it is chosen then, and `COLLATE "C"` is byte-wise on the chosen major (confirmed at Phase 2).
- The Linux cloud container can run a Swift 6 toolchain and a local PostgreSQL (apt or Docker) for server integration tests; otherwise those tests skip and run on the Mac mini.
- Docker Desktop (or OrbStack as the alternative) can be installed on the Mac mini, shares `/Users` with containers by default, and starts at login of the service user without further GUI prompts after the first human-approved launch.
- The SwiftUI and SwiftData APIs relied on (`scrollTargetBehavior(.viewAligned)`, `scrollPosition(id:)`, `onGeometryChange`, `.inspector` and `inspectorColumnWidth`, `NavigationSplitView` with `preferredCompactColumn`, `draggable`/`dropDestination` with a custom UTType, `@Observable`, `#Unique`/`#Index`, multiple `ModelContainer`s, `ModelActor`) are available and stable on iOS 18 (plausibility checked at Phase 1, behavior verified at Phases 4 to 6).
- URLSessionWebSocketTask honors custom `Authorization` headers on the upgrade request, and `tailscale serve` and Funnel pass WebSocket upgrades (verified at Phases 6 and 10).
- Tailscale on macOS issues publicly trusted Let's Encrypt certificates for the tailnet hostname through `tailscale cert`/`serve`, Funnel can expose the same service on 443, key expiry can be disabled per node, and the installed macOS variant supports these CLI features (verified at Phase 10).
- Apple's Sign in with Apple server flow (client_secret JWT signed with the .p8 key, `/auth/token` returning a refresh token usable with `/auth/revoke`, server-to-server notification configuration) matches current documentation (verified at Phase 3); APNs token-based authentication over HTTP/2 and `interruption-level: passive` behave as documented (verified at Phase 8).
- Universal links require a publicly reachable AASA, and the Associated Domains developer mode may allow the household's devices to fetch it from the Tailscale host (verified at Phase 7).
- Fluent plus raw SQLKit can express the savepoint-based idempotency record and the two-pass rank renormalization inside one transaction (verified at Phase 2).
- The MCP authorization specification in force at Phase 9b still requires OAuth 2.1 with PKCE, protected-resource metadata and audience-bound tokens, and whether dynamic client registration is mandatory and what the owner's Claude client supports is confirmed then.
- restic is installable via Homebrew on the Mac mini, the owner has enough iCloud Drive storage for the encrypted repository, and `pmset autorestart` plus service-user auto-login give unattended restarts (verified at Phase 10).
